# tests/btnsites.txt - the BUTTON registry (SPEC.md 20.5.1.3)
#
# `os88ui_btn` IS the standard button and there is no second way to draw one.
# It takes a RECORD and an index, resolves the pressed look from
# OS88UI_BT_DOWN, ORs the erase in itself, and its siblings - os88ui_btninit,
# btnpress, btndrag, btnup - are the SPEC.md 13.7 gesture. btninit installs
# all THREE edges, the press included (OSAPI_WM_ONCLICK, 20.5.1.3.3), so a
# package cannot have a click path that skips the buttons.
#
# `os88ui_btnraw` IS GONE. It was the loose-register painter - a button with
# no gesture - kept reachable while the tree converted one caller at a time.
# Twenty-five call sites were on it and every one is converted; the body is
# private now (os88ui_bdraw, reached by falling through os88ui_btn) and
# t_btnrules fails the build if the name comes back. A scaffold that outlives
# its conversion is the thing the next author finds and copies.
#
# ONE LINE PER FILE: <count> <path>  # <reason>
#
# A file NOT in this list may not draw a button at all - that is the case that
# matters, because it is what a new package hits. A file in it must match its
# count exactly, so the numbers cannot rot in either direction.
#
# WHY A GATE AND NOT A SURVEY: docs/plans/completed/UIHELPERS-PLAN.md 15.4 is a
# survey table of this defect and SEVEN of the ten carriers landed AFTER it
# was written. SPEC.md 13.8.4 predicted that in as many words. A survey cannot
# fail a build.
#
# WHAT THIS CANNOT SEE, and tests/btnall.py can: a caller that draws through
# the record and is wired up wrong. Five shipped that way - a record aimed in
# the click path, one declared on top of the package's own state, a count
# written after the draws, a press hit-tested in the wrong coordinate space,
# and a whole click handler left unconverted. Every one was found by a person
# looking at a screen, because a press-fired button and a release-fired one
# are THE SAME PIXELS in every still.
