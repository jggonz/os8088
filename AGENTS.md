# AGENTS.md

Guidance for Codex and other coding agents working in this repository.

`CLAUDE.md` and `AGENTS.md` carry the same repository guidance. Update both
when changing a rule or lesson; only their titles and introductory agent
descriptions differ.

## Before designing anything: `docs/INDEX.md`

**Read `docs/INDEX.md` before writing a mechanism of your own.** Every `OSAPI_*`
slot grouped by subject, the shared `apps/os88*.inc` includes, the packages as
worked examples, and every SPEC.md section. If the OS already provides it, use
the OS's.

SPEC.md answers "how does this work" and grep answers "where is this symbol".
Neither answers the question that comes first - "is there already a way to do
X" - and the cost of not asking it is a package that reinvents a convention and
looks foreign on the system it runs on. SHEET and CHART shipped with no
`OSAPI_ABOUT_SET` handler (SPEC.md 12.2) while seventeen other packages had one,
because a Help menu got invented instead.

The index is GENERATED by `tools/os88index.py` and checked by every `make`, so
it cannot drift. Add a slot or a package, then regenerate it.

## What this is

os8088: a Macintosh System 1-style GUI OS for the Intel 8086, written entirely
in real-mode NASM assembly, booted from floppy. Pre-emptive multitasking,
overlapping windows, serial mouse, a bottom dock, and loadable software
packages that run as closable, multi-instance apps. One binary drives VGA,
Hercules or CGA, picked at boot.

os8088's DOS (`apps/dos/`, `kerndos/`) is a clean reimplementation of DOS, not
an emulator: call it "DOS", never "the DOS box" or "the box" - DOSBox is an
unrelated emulator.

This file is a map. Each document below is the authority on its subject and
nothing here duplicates it — a second copy is a copy that goes stale.

## Fast fullscreen VRAM games (SPEC.md §53, §109.5)

Use [WireBall's renderer](apps/wireball/wbvideo.inc) and
[game loop](apps/wireball/wireball.asm) as worked examples. The contracts are
§53.4 (mode info), §53.7 (legal calls) and §53.10 (page selection);
[PERFORMANCE.md Set 160](PERFORMANCE.md#set-160--wireball-local-serial-collisions-and-pixel-movement-on-the-xt-specmd-1095)
records the measurements. These techniques belong inside an exclusive
`OSAPI_FSX_RUN` bracket. A windowed game still uses the desktop's clipping,
damage and drawing APIs.

**Choose by capability, then prove the page is usable.** Ask
`OSAPI_FSX_CAPS` for your window's current display, set an offered mode with
`OSAPI_FSX_MODE`, and use its `FSI_*` geometry and framebuffer segment. An
advertised `FSI_PAGES` count alone does not grant access to a second page:
check `OSAPI_FSX_PAGE`'s carry flag before writing there. WireBall uses:

| Adapter and mode | VRAM layout in that mode | Presentation |
| --- | --- | --- |
| VGA, 320×240 Mode X | two of the three pages, offsets 0 and 19,200 **per plane** | `OSAPI_FSX_PAGE` |
| Lone Hercules, 720×348 | offsets 0 and 8000h in B000h | `OSAPI_FSX_PAGE` |
| CGA/EGA, 640×200 mono; Hercules with a color card | one page | `OSAPI_FSX_WAIT`, `FSXW_VSYNC`, then short changed spans |

Those offsets describe these modes, not arbitrary framebuffers. Hercules
page 1 occupies physical **B8000h**, the color card's aperture on a dual-card
machine; the page API refuses it there. Keep the single-page path. Select
page 0 before leaving a flipping bracket; return through FSX so the kernel
restores the desktop, video configuration and clock. Do not replace these
APIs with private CRTC flips, BIOS mode sets or PIT channel-0 programming.

**Draw the hidden page, then show it.** Initialize the static court on every
page and establish which page is displayed before starting the loop. Draw
the next scene into the other page, call `OSAPI_FSX_PAGE` to show it, then
switch the drawing target. The API waits for the retrace that latches the
page; after it returns the other page is safe to modify. An extra VSYNC wait
before the flip spends another refresh. Flipping changes the display address;
it does not copy a RAM framebuffer. A single-page retrace wait is only the
start of a short drawing window, not a promise that unlimited writes fit in
blanking or that real CGA hardware cannot snow.

**Damage history belongs to each VRAM page.** Keep separate old sprite
rectangles and HUD caches for each page: its pixels are from the last time
that page was drawn, not the last displayed frame. Skip unchanged rectangles.
For a vertically moving solid paddle, retain the overlap, erase only the
exposed end strip and paint only the newly covered strip; use a full update
when dimensions change or the rectangles no longer overlap. WireBall's
black court permits erasing to black. On a patterned background restore the
background and redraw intersecting sprites in order. Cache the HUD's small
state signature **before** building strings or comparing glyphs, then draw
only changed cells. Copy `OSAPI_FONT_GLYPHS` before entering the foreign
mode, as WireBall does; desktop drawing slots are off-limits in that mode.

**Make the inner loop match the adapter.** In Mode X, up to four adjacent
pixels share one byte offset in different planes. Group equal-color pixels
under one sequencer map mask and write once; mixed-color pixels need their
own plane data. For narrow packed-mono sprites, combine the end masks into
one byte or word read/modify/write, preserving neighboring bits. Calculate
the first scanline address once, then advance by additions through the
2000h banks: two interleaved banks with 80-byte rows on CGA, four with
90-byte rows on Hercules. Avoid multiplication, port writes and mask
branches per pixel when their result can be reused across a span. A full
screen clear belongs at initialization or a scene change, not every frame.

**Physics and presentation have separate clocks.** Catch up fixed motion
steps, prepare the next page immediately, then let presentation wait for
retrace. Waiting for a motion deadline before drawing can miss retrace and
reduce the display rate. WireBall requests `FSXF_RATE` with divisor 2048
(about 582 Hz), accumulates the hook's elapsed-period count and advances
motion every eight periods (about 72.8 Hz). OS ticks retain 18.2 Hz sound,
serve and link deadlines. Keep fractional positions through simulation and
convert to whole pixels at drawing time; use the same extents and coordinate
scale in the collision checks and the visible sprites. `kern_small` refuses
`FSXF_RATE`: handle that refusal with a supported slower/text fallback.

**Retrace waits still owe the hardware service.** An original 8250 has a
one-byte receive buffer; at 2400 baud 8N1 a byte takes about 4.17 ms, less
than a refresh. WireBall's short rate hook captures UART bytes/status and
advances queued TX while the foreground waits. It publishes completed queue
entries last; parsing, commands, collision work and rendering stay in the
foreground. Follow §53.2.2's hook restrictions: no kernel calls, at most
48 bytes of stack, and the documented interrupt/register contract. The hook
is armed before the entry proc runs: guard device access with a readiness
flag until initialization is complete. Disable device service
before restoring borrowed UART/PIC state. See
[the hook and queue](apps/wireball/wblink.inc). Poll between bounded work
chunks in a fallback without a rate hook.

**Measure an active rally on the emulated XT.** QEMU checks behavior and
serial bytes, not 4.77 MHz speed. In the final pass described below, use
MartyPC's guest cycles with held-key motion, wall/paddle hits and no pause or
serve countdown; report display frames and physics steps separately.
WireBall's `wireballvideo` row checks VGA, CGA, lone Hercules and dual-card
Hercules, page counts, exact sprite occupancy after movement, fractional
controls and restored desktop/input state. `wireballphysics` checks swept
contacts and their cycle budget. Include real serial traffic when changing
the renderer's service budget. Set 160 measured 46–59 display frames/s and
about 73 motion steps/s, not a guarantee for every game or physical XT.
Read [Hercules testing](docs/HERCULES-TESTING.md) and
[MartyPC debugging](docs/MARTYPC-DEBUG.md) before interpreting raster captures
or changing the emulator's page mapping. Name the relevant rows during
implementation; run their deduplicated union once after the last batch.

## Commands

**`make deps` FIRST, on a box you have not built on.** It installs nasm,
qemu, pkg-config and libudev-dev, and is ~0.2 s when they are already there.
A fresh Linux container has `cargo` and `python3` and none of the rest, and
the failure that costs is `make marty` compiling most of MartyPC before cargo
dies on a missing `libudev.h`. Also needed: `python3` **3.11 or newer**
(`tools/` imports `tomllib`; Apple's 3.9 fails every `make`) and `cargo` for
`make marty` (rustup, which `make deps` does not install). No linker -
everything is `nasm -f bin`.

```
make deps          # host dependencies; `make deps-check` reports only
make               # every shipped floppy into build/, plus the doc gates and the fast tier
make help          # EVERY target and knob, one line each - start here for anything below
make run           # QEMU with a serial mouse; RUNAPPS=<img> swaps B:
make marty         # MartyPC, the cycle-accurate 8088 - build it at the START of a session.
                   #   A run past ~180s has FROZEN, not slowed: diagnose it
make test          # QEMU headless, QMP at build/qmp.sock (the fallback instrument)
make test-fast     # the three test tiers - the Testing section below says
make test-full     #   when each is run; none of them is a per-commit gate
python3 tools/os88test.py soak -k 'disp*'   # soak rows, scoped - the usual answer
python3 tools/os88soak.py check|start|status -k ...   # the same, parallel and
                   #   detached, with a preflight and --resume; HOLD A WAITING
                   #   TASK for the whole run in a container, or it dies
python3 tools/os88bisect.py classify <row>  # why a row fails, sampled not guessed
make small         # kern_small (the 128KB machine) into build/smallk/
make emu           # kern_emu (kern_big + VMware absolute pointer) into build/emuk/
make mega          # kern_mega (286+ protected mode) into build/megak/
make clean
```

**Everything else is in `make help`**: the application disks, the gate disks,
the live media, the ROM, the bundles, ~60 build knobs and ~80 86Box machines.
Each is one line there; the detail is the comment block beside its rule
(`grep -n '^<target>:' Makefile`, or `grep -n '^#> .*<KNOB>=' Makefile`), and
SPEC.md is the authority on what each thing IS. `tools/os88help.py --check`
runs in every `make`, so a target named here without a `#>` marker beside its
rule fails the build.

What `make help` cannot tell you:

- **Knobs are stamp-tracked**, so changing one rebuilds what it reaches - and a
  knob kernel left in `build/` is what every later boot and every symbol lookup
  sees. Build knob kernels into a private tree (`make BUILD=<dir>`,
  `tools/os88build.py`). **`make -n` with a knob pointed at `build/` is NOT a
  dry run**: the stamp rule deletes `kernel.bin` and every boot sector while
  make parses.
- **Nothing in `build/` is tracked - never commit a binary.** The toolchain is
  deterministic (`os88disk.py` pins the volume serial and every FAT
  timestamp), so any image can be rebuilt byte for byte.
  **One sanctioned exception, the owner's (2026-11-05)**: ARCADE's
  ROM-free translated parts in `apps/arcade/prebuilt/`, so neither `make`
  nor a release needs the ROMs or archive.org. `make arcadeprebuilt`
  refreshes them, and the fast-tier `arcprebuilt-stamp` fails `make` when
  their inputs move without them (ARCADE-SPEC 1.6).
- **Fetched data is never committed** (Frotz stories, Lemmings, the Apple II
  ROMs, RunCPM's master disk, the soundfont): the targets fetch it at pinned
  hashes, and `make clean` spares what it fetched.
- **On-demand targets are not in `all`**: a `make` that passed has not built
  the C toolchain, the application disks or the gate disks.
- **86Box machines** are one per `vm/` directory (docs/86BOX.md). `pc5150` is
  the owner's own machine, where most bug reports come from. `386-ps2` is the
  only PS/2 mouse, `286-525` the only 1.2MB drive, `xt-multimon` the only
  two-card XT and `xt-wire` the only NIC. The PicoMEM profiles launch through
  `tools/os88box.py`, not make. `RESET=1|flash|both` clears a machine's CMOS
  or flash on the way in; on an AT that means one stop in BIOS setup.

## Building an app or game in waves

Use WireFleet's delivery workflow for new applications and games, unless the
user gives a different workflow. `apps/wirefleet/` and its SPEC.md section
(§114) are the worked example of the result.

1. **Isolate the work.** Read `docs/UPSTREAM.md`, fetch the current base and
   create a named feature branch in a separate git worktree. Leave the user's
   existing checkout, local changes and running VMs alone.
2. **Map the OS before designing.** Read `docs/INDEX.md`, the applicable
   contracts and a shipped package that already solves the closest problem.
   Reuse APIs, shared source and interaction conventions. Record a missing
   facility or ownership boundary explicitly; do not copy a peer's mechanism
   into a context where its guarantees no longer apply.
3. **Write the contract and delivery stories first.** Pin interfaces, data
   formats, rules, memory costs and adapter behavior in the appropriate SPEC
   before implementation. Keep a checked story list in `docs/plans/`, with
   concrete user-visible outcomes and verification for each wave. Distinguish
   planned behavior from behavior that actually works.
4. **Keep one review thread.** Open a draft PR for the foundation, then commit
   and push each reviewable wave to that same branch and PR. Update its
   description and checklist to reflect the current implementation and actual
   evidence. Keep working through the authorized stories; a wave boundary is
   not a reason to ask permission to continue. Do not merge without the user's
   instruction.
5. **Treat artwork as source.** When bitmap artwork benefits the product, use
   image generation as requested or appropriate, retain the selected source
   and exact prompt, and build runtime assets through a deterministic host
   converter. Include explicit monochrome assets when the supported adapters
   need them. No generation service belongs in `make` or on the guest.
6. **Keep a "How It Was Built" diary as the work happens.** Store it with the
   repository documentation, link it from the plan, and write for later reuse
   on the website: user stories, decisions, constraints, discoveries, pictures
   and measured results. Separate observations from intentions, and name what
   was actually tested. Updating the diary does not authorize website
   publication.
7. **Verify each wave at the right level.** Use host builds/checks and a boot
   to look during implementation; name the affected suite rows. Respect the
   Testing section below: run the deduplicated soak union and `test-full`
   after the final batch, not once per wave. Finish with the actual supported
   adapters, sound/link configurations and resource cleanup checked, and report
   hardware-only limitations honestly. Do not mark unfinished stories done.

## Hard rules (§1 — these break silently if violated)

- **8086 only.** `cpu 8086` plus `-w+error`: no `pusha`, no `push imm`, no
  `shl reg, imm` other than 1, no `movzx`, no 32-bit registers.
- **Near model.** CS = DS = `KERNEL_SEG` for kernel code and every task;
  **SS = `LOW_SEG`**, because task stacks live outside the kernel's segment.
  Every inter-module kernel call is near — there is no far code (§33).
  **SS ≠ DS, so `[bp+disp]` addresses SS**: kernel code holding a pointer in BP
  needs `[ds:bp+…]`.
- **Register discipline.** Public routines preserve every register but their
  documented outputs. ISRs push DS/ES, load DS = KERNEL_SEG, `cld` before
  string ops. Critical sections are `pushf`/`cli` … `popf`, never `cli`/`sti`.
- **Section discipline.** A module switches sections with a bare
  `section <name>` and **must switch back to `.text` before the file ends**, or
  the next include lands in the wrong one.
- **Label hygiene.** One flat namespace: every module-internal label carries
  its module prefix (`vga_`, `wm_`, `menu_`, `fm_`, `dsk_`, …) or is a NASM
  local label.
- **A toast message is a `TOASTSTR`, never a bare `db` (§59.10.1).**
  `TOASTSTR label, 'text'` (or `TOASTRUN label` ... `TOASTEND` round a run
  with fields poked at run time) emits the same bytes and FAILS THE BUILD at
  that line past `TOAST_MAX` (24) - the bar drops the rest silently. In C,
  hand `os88_toast` a literal. `tests/unit/t_toast.py` follows every toast
  argument back and fails on anything else; text only the running program
  knows (a name, a number) goes in `tests/toastdyn.txt` with its reason.
- **Text is `font_run`, not `font_str` (§6.1, §6.6).** `font_char`/`font_str`
  are TRANSPARENT — they leave what is underneath — so a `gfx_fill` followed by
  one of them writes every pixel twice, and the gap between the two passes is
  *visible* on the target machine. `font_run` draws the ground and the glyph in
  one pass. Transparent text is a **closed list of six cases** (§6.6.2) and
  `tests/textsites.txt` is the ratchet: a new call site fails the build until it
  is registered with a reason, and the count can only go down. **The sweep is
  finished** (§6.6.5): the registry stands at 70 sites in 21 files, every one
  with a reason, so a new transparent call is now an argument to win rather
  than a queue to join.
- **Three adapters, one binary (§39).** `SCREEN_W`/`SCREEN_H`/`ROW_BYTES` are
  VGA *reference* values, not the truth — the live screen is
  `[vid_w]`/`[vid_h]`/`[vid_stride]`. Anything that clips, centres or anchors
  to a screen edge must read those, or it is wrong on two adapters of three.
  **Look at a drawing or greying change on a 1bpp adapter before calling it
  done** (§39.4, §47): grey rounds to black there, so a disabled glyph is a
  checkerboard and a ring is dotted.
- **Code only a VGA or an EGA runs goes in `.vga`, behind a RUN-TIME door**
  (SPEC.md 2.10.9). On kern_big the rung sits inside KERNEL_SEG's window, so
  calls into it stay near, and a CGA, Hercules or MDA machine slides `.cold`
  down over it at boot - after which a call into it runs `.cold`'s bytes.
  Every way in from outside is registered in `tests/vgarefs.txt` with the
  test that keeps those machines out (`[vid_planes]` = 4, `[vid_avail]`);
  `%ifdef GFX_VGA` is not one, kern_big defining it on every machine. The
  rung may not name `.cold`'s segment (a `.text` shim makes that call), and
  a row reading a `.cold` label on a mono machine goes through `m.sym()`,
  which follows the slide.
- **Every disk-visible base is 512-byte aligned.** int 13h answers a transfer
  straddling a 64KB physical boundary with error 09h, and only starting
  512-aligned prevents it. The symptom is "Disk error" on a large save.
- **Memory is THREE rules and three quantities** (docs/KERNEL-MEMORY.md):
  **kern_big fully RESIDES in 100KB at the desktop**, **kern_small fully
  RESIDES in 64KB** — every non-purgeable byte, no drivers, no XMS, on VGA
  (guard 1's `KERN_BUDGET`, DERIVED from those, plus `tests/kernresident.py`
  and `tests/small128.py` for the half an assembler cannot see) — and **BOTH
  BOOT on 128KB** (guard 5, `MIN_RAM_KB`, asserted by booting each kernel on a
  128KB machine). **kern_mega is rule 4 and is budgeted too** (kern_mega size
  `MEGA_RESIDENT`): it RESIDES in **68KB of
  CONVENTIONAL memory** once it has switched - `MEGA_RESIDENT`, `KERN_SIZE`
  less the `.cold` and `.mega` rungs that go above 1MB, and NOT `KERN_SIZE`,
  which is a boot-time transient there - and BOOTS on its 1MB floor machine's
  640KB (guard 5's mega arm, `MEGA_BOOT_KB`); budgeted is not RELEASED, and no
  release artefact carries its disks. **A budget is met EXACTLY at an upstream merge or a release;
  branch and integration work may run up to 2KB over it** (`KERN_GRACE` —
  features land whole and are size-passed after), and `make budget-check` is
  where that grace ends, on all four budgeted kernels. Over a budget at that point is a conversation with
  the owner and a rework of the budgets, never a quiet raise.
  `KERN_CODE_MAX` is separate and absolute: `.text` + `.bss` inside one 64KB
  window because offsets are 16 bits. **Booting on a machine and residing in
  one are different questions** — the 128KB boot is where overlays and boot
  order broke machines whose resident size was well under it. `kernsize`
  prints both lines; quote the one you mean. **None of the rules binds a KNOB
  build** — guard 2 is the whole of what
  bounds it, because nobody boots one and every machine here has 640KB or
  could; a RAM-constrained test states its own constraint instead.
  `KERN_SMALL`, `KERN_EMU` and `KERN_MEGA` are not knobs for this purpose;
  a knob ON kern_mega (`MEGATRAP=1`, `MEGADIAG=1`, ...) is. **`soak -k 'buildmatrix'` is
  the only thing that builds the knob kernels.**
- **Before spending a resident byte, ask whether the feature is an ON-DEMAND
  MODULE** (§2.8, `kernel/mod.inc`): kernel code that ships as a file (`CTRL.DRV`, `FORMAT.DRV`,
  `DISKOPS.DRV`, `HIBER.DRV`, on kern_big `DOCK.DRV`, `EXTD.DRV`,
  `WIN95.DRV`, `DESK.DRV` and `STIKMENU.DRV`, and on
  kern_small `FILECP.DRV` and `FDLG.DRV`) and
  is read into a heap claim when the feature is asked for, freed when it is
  done. A feature qualifies when the system disk is already required to use
  it, or can be required without interrupting what the user was doing. When
  it qualifies, the resident part is the menu item, the greying predicate and
  the thunks; everything else goes in the module. Only a feature that fails
  the test may grow `.text`/`.cold`, and moving code to `.cold` or the boot
  overlay relieves `KERN_CODE_MAX` but not `KERN_BUDGET` — a module relieves
  both. Check `tools/kernsize.py` before and after: a byte costs a byte.
  **Code `mod_need` itself reaches cannot be a module** - the loader cannot
  load its own dependencies - so code inside that cone is gated by build
  rather than moved. There is no entry cap (§2.8.1): a module's slot block is its
  own entry count.
  **"Freed when it is done" is GATED**: `tests/unit/t_moddrop.py` (fast)
  fails `make` for a `mod_tab` row nothing drops, unless
  `tests/moddrop.txt` says why it is held until restart - `DESK.DRV` held
  5KB pinned after the last Sticky App closed, until SPEC.md 11.103.10's
  drop rule. A new module needs its drop on the day it lands.
- **kern_mega-only package code is the ARM's, never the shipped build's**
  (SPEC.md 20.18). The owner's rule:
  *"mega specific work that more than trivially increases the disk size is
  gated to mega builds only."* Code a package carries only because segments
  may be SELECTORS - a second ISR family for protected mode, a decoder part
  assembled to write nothing through CS, reads through a run of selectors,
  a path for a claim that is an LDT selector - goes under `%ifdef PKG_MEGA`
  (apps/os88mega.inc), and `make mega` builds that arm onto kern_mega's own
  disks. On kern_mega a claim is an LDT SELECTOR, so a package asks
  `OSAPI_SEG` (§50.6.11) for a derived segment rather than adding to one. The shipped build must still be CORRECT on kern_mega: run low and
  plain, refuse the one tier, or refuse to start with `OS88_MEGA_REFUSE`,
  and say which at the place. `tests/unit/t_megapkg.py` (fast) fails the
  build when a shipped build assembles a kern_mega marker (`CPU_F_PM`, the
  selector cells) beyond `tests/megapkg.txt`'s per-file allowance - which
  turns one way - or takes a part assembled `-DVB_PM`/`-DPKG_MEGA`, or names
  `PKG_MEGA` with no arm in `$(MEGAPKGS)`. A new arm is a `$(MEGAAPPDIR)`
  rule and a `$(MEGAPKGS)` entry in the same diff.
- **An ABI change is a written decision** (§20.2.0.1). `PKG_FMT` and
  `DRV_VER` are locked in `tools/abi.lock.json` to a fingerprint of
  `apps/os88api.inc` and `drivers/os88drv.inc`, and `make` fails when the SDK
  moves under them. Bump the number if anything built before can no longer
  run (a cell moved or re-contracted, a header grew), then
  `python3 tools/abilock.py --update "why"`; if it still runs (a cell added at
  the end, a contract clarified), the same command without the bump.
- **A heap claim can MOVE, and the default is that it may not** (§66). A record
  is born `MC_RLOC` = 0, PINNED; `OSAPI_MEM_MOVABLE` opts one in and takes a
  relocation **proc**, not the address of the word naming the block — a holder
  can have more than one such word, and segments derived from a base are
  reached by no poke at all. Opting in and forgetting the proc is silent until
  the next compaction, which by construction happens on a busy heap.
- **The package boundary is solved once, not per call site** (§20): calling out
  is a far call through an API cell that switches DS; calling in goes through
  the three-byte dispatcher in the package header, so every callback is a near
  proc with a near `ret` and a package author never writes `retf`; and
  **ES = KERNEL_SEG on entry to every callback**, so it is `[es:bx+W_W]`, never
  `[bx+W_W]` — without the override a package reads its own image at that
  offset, which assembles cleanly and runs wrong.
- **A package reaches the network through a DRIVER, not through the kernel**
  (§72): `ETHER.DRV` publishes the socket surface as `OSAPI_DRV_CALL` verbs, so
  the kernel learns nothing about TCP and a machine with no card refuses at the
  one fence. `apps/os88sock.inc` is that ABI written once; `apps/os88line.inc`
  is the line discipline Telnet and the browser share.
  **A socket buffer must live in the package's own segment**: `OSAPI_DRV_CALL`
  is an X stub and puts the caller's segment in ES, so a staging buffer in a
  heap claim is read out of the package's own image instead — which reads as
  memory corruption rather than as a wrong segment register, because the bytes
  really are ours (§77.10).
- **A worker may not touch a file** (§20.6 rule 7), so a package that is
  socket-to-file by definition is shaped around `OSAPI_WM_ONWAKE`: the worker
  stages, the UI task commits, and a single byte written last by the producer
  and cleared last by the consumer is the whole handshake — no lock, because
  the worker may not take one. `apps/ftpd/` (§77) is the worked example.
- **A C package that does not fit gets a second segment, not a bigger one**
  (§73.14): a function named `ovl_*` has its CODE emitted into a module that
  is far-called both ways - shipped as a PART of the package itself with
  `CC_OVL_PART` (§73.14.2, CWORD's shape), or as a `<NAME>.OVL` beside it - while
  every global, literal and bss byte it names stays resident and DS-relative. Split by
  FREQUENCY — a keystroke's path stays in, a menu command's can go out — and
  never take the address of an overlay function.
- **A C package obeys four extra rules, and `tools/cc8086.py` fails the build
  on each** (§73, docs/C-TOOLCHAIN.md): **never take the address of an
  automatic** — SS ≠ DS, so `&local` is a stack offset dereferenced through the
  package segment, and every addressable object must be `static`; **no
  `movs`/`stos`/`scas`/`cmps`** — ES is the kernel's, so no struct assignment,
  no struct by value, no struct return; **no `long`, `float`, `double`,
  bit-field or anonymous union**; and **frames stay under 96 bytes**. The first
  two are one defect with two symptoms — a struct passed by value trips both —
  and both are silent without the gate.

## Performance (PERFORMANCE.md, condensed)

The target is an **IBM PC/XT — 8088 at 4.77 MHz** — and you are testing ~1000×
faster. **QEMU is exact about how much work the guest does and useless about
how long it takes.** Estimate with these, measured on a real 5150:

| | cost |
|---|---|
| any `gfx_*` drawing call — the FIXED PART, not the call | **756 us** (measured small: an 8px hline, a pixel. A real one is more — a 6px `gfx_hline` is 678 us and a 312px one 862; `gfx_frame` on an 11x11 box is 3.4 ms. **Never quote 756 as a floor a design must beat** — Set 89) |
| one coalesced RUN of a 4bpp blit, VGA, direct | **~377 us** (1,797 cycles — and, like the row above, near enough flat in the run's length. A dithered picture is one run a PIXEL, which is what §5.4.1.3's decoder exists for) |
| one 8×8 glyph cell | **~900 us** |
| one 78-cell row of text | **~71 ms** |
| an `OSAPI_*` far call / a near `call`+`ret` | 46.7 us / 11 us |
| `OSAPI_TASK_YIELD`, a full task switch | 693 us |
| one `int 13h` call, near enough whatever it moves | **~400 ms** (1–2 disk revolutions) — cost disk work in **calls**, not sectors |
| system tick | 18.2 Hz |

> **A redraw is priced by how many primitive calls it makes, not by how many
> pixels it covers.** Almost everything else follows from that sentence.

The rules that fall out:

1. **Nothing repaints more of the screen than it changed.** This is the
   architecture, not an optimisation — §11.3's clip region, §11.90/§11.91's
   damage rects, §11.92's title strip, §28.2's chunks. Part 5 of
   PERFORMANCE.md is the standing budget: **a change that reintroduces a full
   repaint is a regression against a documented number, not a neutral
   refactor.** Check yourself against that table.
2. **Nothing writes a pixel twice.** The erase-then-letter pair is the
   canonical violation and `font_run` (§6.1) is the answer: one decision per
   cell, so the line is never momentarily blank.
3. **Size every range from the slowest machine it will run on.** A constant
   sized while looking at QEMU encodes the wrong range and fails structurally,
   not proportionally: 16-bit counters lap into small plausible numbers. Fold
   into 32 bits per iteration.
4. **Measure before redesigning; a counter is not a timer.** Put a counter in a
   primitive (`font_char`, `gfx_fill`, `wm_paint_all`) — it costs one rebuild —
   then multiply by the table above and say that you did. A clock is
   `apps/os88pit.inc`'s `pit_now` (838 ns, an hour before it wraps), never a
   hand-rolled PIT latch: one misses the tick at the reload. When you PROFILE
   the kernel, resolve a sample by LINEAR address (`os88sym.linear()`), never
   by offset against the `.text` table — the kernel is several segments and a
   `.cold` sample resolved against `.text` returns a plausible WRONG name —
   and aggregate by routine, since a `.local` label belongs to the proc above.
5. **Keeping the shape of an optimisation is not keeping the optimisation.**
   `gfx_blit4`'s first version emitted exactly the designed number of calls and
   decoded every pixel by hand inside them: nine times slower, and QEMU priced
   it identically. When you rewrite something whose *reason* is speed, verify
   the reason survived, not the structure.
6. **Refusal is a normal path.** Do not ship a feature that silently costs
   seconds on the target; ship one that greys itself with the reason (§47 —
   grey a fact, never a guess).
7. **Degrade by tier.** `OSAPI_CPU_INFO` answers `CPU_8086` for the target
   machine, which is a fact the code can test rather than a guess about speed.

Three defects are **invisible in an emulator** and cost this project bug after
bug: a **visible redraw** (seconds on real hardware), a **double-draw flash**
(anything drawn twice), and **input overrun**. None showed in a screendump;
every one was found on hardware or by counting.

That is the whole of it that applies to every change. Open PERFORMANCE.md
itself for one of four reasons — it is 6,553 lines and over half is a log of
field measurements:

- **Part 5** before touching a redraw path — the standing budget names the
  operation, what it used to cost, what it costs now and the § that owns it.
  If your path is in that table, that row is the bar.
- **Part 2** when you need a number you are going to quote. It carries the
  access-shape distinctions this summary flattens (a sector inside a coalesced
  run vs. an isolated seek; the 8088's `max(clocks, 4.34 × instruction bytes)`
  fetch floor, which is why a shorter encoding can beat a cheaper instruction).
- **Part 7** when checking a change, and **Parts 3.1/3.2** when measuring
  flicker or smoothness — those are the harness manuals.
- **Part 9** only to find where a number came from, or when taking a new field
  set. Never as briefing.

## Testing

**There is a regression suite now** — `make test-fast` / `test-full` /
`test-soak`, driven by `tools/os88test.py` off the registry in
`tests/suite.py`. The fast tier runs as part of every `make`; **`test-full` is
the pre-merge gate**. There are still no unit tests in the usual sense: the
rows are host-side invariant checks over what `make` just built, the build
configurations `all` never builds, and whole scripted sessions driven through
an emulator.

**Soak and `test-full` run ONCE, after the last batch** (the owner's rule).
When a change lands as batches or waves — review-fork-pr's `fix.js`,
port-to-os8088 and native-game-port waves, refresh-stale-pr fixes, any agent
fix series — no batch runs a soak row or `test-full`. A batch verifies on the
host (`make`, which runs the fast tier; `make KERN_SMALL=1`;
`tools/kernsize.py` on both kernels; pure host checks) and NAMES the
`tests/suite.py` rows covering what it changed. After the last batch, one
`os88test.py soak -k … -k …` call runs the deduplicated union — any A/B leg
against the starting commit in that same pass — then `test-full` once. A soak
row is minutes, and a per-batch rerun buys no new information.

What counts, because isoTron's six waves spent **about eight of their
nineteen hours** on emulator rows while obeying the letter of a narrower rule:

- **A row is a row however it is started.** `python3 tests/<row>.py` run by
  hand, a row launched in the background and polled with `until … sleep`, a
  shell loop over row names and a scratch MartyPC script that measures what a
  row measures are all soak runs. 531 direct script calls and 285 minutes of
  polling were the larger share of those hours, and neither said `soak`.
- **Every role in a batch is the batch.** Implementer, fixer, reviewer,
  verifier and repairer alike: an independent verifier checks a wave on the
  host and by LOOKING (one boot, screenshots cropped and zoomed). A boot to
  look at the picture is not a row; re-running the rows is.
- **A measurement is taken in the final pass, not per wave.** A wave whose
  acceptance is a MartyPC number names the row that produces it, and the
  final pass produces it. The one exception is a number that DECIDES a
  design (which renderer, which table size): the agent choosing takes it
  once, writes it in its report, and nobody re-takes it to confirm.
- **Never wait for host load before a cycle measurement.** MartyPC's cycle
  counter is emulated and host load cannot move it; only the rows with a
  wall-clock budget care, and those run in the final pass anyway. isoTron's
  agents sat in `loadavg` loops for up to eight minutes at a time.
- **A failing final pass re-runs only what failed.** Fix, re-run the failing
  rows, and run `test-full` again only if the fix touched code outside them.
- **A brief does not override this.** A workflow prompt that says "run the
  wave's tests" means the host checks and naming the rows. The workflow
  scripts under `.claude/skills/` are written to this rule; a new one must
  be too.

Everything else is still boot `make test`, then drive it over QMP.

```
python3 tools/mouse.py build/qmp.sock click 180 150        # absolute click
python3 tools/mouse.py build/qmp.sock to X Y / down / up   # menus: press, drag, release
python3 tools/mouse.py --screen 640x200 build/qmp.sock ... # MUST match the adapter (§39)
python3 tools/qmp.py build/qmp.sock 'sendkey h'
python3 tools/shot.py build/qmp.sock out.png [--crop X,Y,W,H] [--zoom N]
python3 tools/qmp.py build/qmp.sock 'quit'
```

docs/TESTING.md is the authority on which emulator to reach for, and its
opening currently argues MartyPC first — so expect it to disagree with the
paragraph above.

**Entries 1, 2, 4, 5 and 6 also run on 86Box, on the row's own kernel and
disks** (`OS88_EMU=86box`, registered as `box-<row>` in
`tests/box86port.txt`; docs/86BOX.md, *kern_big rows on 86Box*): a period
BIOS rather than SeaBIOS, and still no timing.

Four traps not written down elsewhere:

- **Never hand `/dev/null` to nasm as `-o` or `-l`.** A failed assembly
  unlinks its `-o` target and `-l` replaces its target with a regular file, so
  as root the device itself is replaced and everything after misbehaves
  without naming the cause. Write to a temp file. `tests/unit/t_nulldev.py`
  refuses the pattern in the tree; `stat -c %F /dev/null` must say
  `character special file`.

- **A knob kernel in `build/` is a different kernel to the symbol reader.**
  Every emulator row resolves kernel symbols through `tools/os88sym.py`, which
  re-assembles `kernel.asm` and refuses an address unless the result is
  byte-identical to `build/kernel.bin`. A commit does NOT trip it — the About
  box's build number is the commit count (§14.2), and `os88sym` reads the
  number out of the image and assembles with that one — but a `VIDEO=` or
  `RTC=` kernel left in `build/` does, and every row then dies saying "the
  map describes a DIFFERENT kernel", which points at the kernel rather than at
  what you did. Pass the knob's `--define` (or `$OS88_DEFINES`), or build
  knob kernels into a private tree with `tools/os88build.py`. `os88test.py`
  checks once, before any row runs, and deliberately does not rebuild,
  because a preflight `make` would silently overwrite the build under test.

- **A previous session's QEMU may still be running.** `make test` then fails
  with `cannot create PID file`, but the stale instance keeps answering on
  `build/qmp.sock` — every screendump succeeds and shows the OLD kernel, which
  reads exactly like a change that did nothing. If the error scrolls past,
  `ps aux | grep qemu-system` and compare its start time against
  `build/kernel.bin`'s mtime. **Kill it with `pkill -f "[q]emu-system"`, in a
  command that does not itself mention QEMU** — `-f` matches the killing
  shell's own command line, so the bare pattern kills that shell and so does
  the bracketed one if a relaunch shares the line: exit 144, no error text,
  nothing dead, and every command after it silently skipped.
- **A small change is easy to misread as "nothing happened"** in a full-screen
  dump. Crop and zoom (`shot.py --crop --zoom`) before concluding a click was
  lost.

Mouse pacing, double-click timing, the writable scratch images and when to
reset them, 86Box's config rewriting, and what each emulator can show are all
in docs/TESTING.md, per capability.

## Layout

- `boot/boot.asm` — the 512-byte boot sector, which now does one thing: read
  `boot/boot2.asm`'s blob, check it, and enter it (§2.9). The loader proper is
  in the blob, because 512 bytes stopped being enough. Geometry and kernel size
  are injected by the Makefile, and stage 1 relocates itself.
- `kernel/kernel.asm` — constants, the memory ladder and its guards, boot
  sequence, the API jump table, `%include`s of every module, size assertions.
  Which `.inc` owns what is the table in §4. The pre-GUI shell's unincluded
  leftovers — `video.inc`, `keyboard.inc`, `string.inc`, `gfx.inc` — are gone
  (§4); `softgfx.inc` is what replaced the last of them.
- `apps/` — loadable packages; **everything here ships**. `os88api.inc` is the
  SDK, and each package's design notes are its SPEC.md section. `apps/cc/` is
  the **C** SDK (§73): `os88.h`, the runtime `crt0.asm`/`os88thunk.asm`, the
  build rules, and `ccsmoke` as the worked example.
- `drivers/` — loadable drivers (§51): same format, but `.DRV`, header version
  4, no instance record, bss shipped inside the image. `drivers/ether/` is the NIC
  and the TCP/IP stack (§72) — the largest of them, and QEMU-only to test.
- `tests/` — every package that is **not** shipped software: capability gates
  (pass/fail) and benchmarks (how fast). Built only by their own targets.
- `apps/browser/`, `apps/telnet/` — the network clients (§71, §70), over
  `os88sock.inc`. `tools/os88proxy.py` is the host-side other end and
  `os88proxygui.py` its desk-side front. `apps/ftpd/` is the FTP **server**
  (§77) — the same ABI listening rather than connecting. SPEC.md §72 is the
  stack, layer by layer, and why TLS terminates in the host proxy.
- `tools/` — host-side Python: `os88pkg.py` (validates/stamps `.bin` → `.o88`),
  `os88disk.py` (builds FAT12 images; `--verify` is a structural fsck),
  `checkdocs.py` (the doc gate every `make` runs), `os88test.py` (the suite
  runner, off `tests/suite.py`), `os88boot.py` (where a whole boot goes, phase
  by phase, off MartyPC's cycle counter and the FDC's - docs/MARTYPC-DEBUG.md),
  `qmp.py`/`mouse.py`/`shot.py` (test drivers),
  `setup-cc.sh` + `cc8086.py` (the C toolchain's fetch and its gate, §73);
  `stkwater.py`/`stkdepth.py` (how deep a task stack HAS been, and which
  call chain took it there - docs/KERNEL-MEMORY.md's "Task stacks");
  `kfzread.py` (the KFZ heartbeat out of a field screenshot);
  `os88intguide.py` (the interactive INTERRUPTS page - the first 1.5KB
  of memory, how the 8088 takes an interrupt, all 256 vectors and which
  ones os8088 and its DOS hook; ON DEMAND, no emulator. Every os8088
  claim on it stands on a source anchor `--selfcheck` re-checks, and it
  will not write a page whose anchors fail. Chapter 2, the BIOS data
  area and the disk path, is docs/plans/INTERRUPT-GUIDE-PLAN.md).
- `docs/` — **the directory says what a document is** (`docs/README.md`, and
  `docs/INDEX.md` lists every one under the same five headings). `docs/`
  itself is how the system works TODAY — instructions, contracts, maintained
  reference such as `KERNEL-MEMORY.md`, and `FIELD-NOTES.md`/`FIELD-MACHINES.md`
  for what real hardware said. **Everything else is NOT where to learn how
  something works**: `docs/plans/` is work proposed or half-done,
  `docs/plans/completed/` is how something got built (never what it does
  now), `docs/history/` is superseded, and `docs/reports/` is a dated
  MEASUREMENT of one tree. They go stale by design; SPEC.md, the docs above
  and the code are the authority. When you write one: a plan whose work
  lands moves to `completed/` in that commit, and a second measurement is a
  NEW report rather than an edit.

## Package pipeline

```
apps/mines/mines.asm --nasm--> build/mines.bin (org 0)
                    --os88pkg.py--> build/mines.o88   (validated, not relocated)
build/*.o88        --os88disk.py--> build/apps*.img   (FAT12 floppy, drive B:)
```

Packages are assembled at org 0 and loaded into a paragraph-aligned heap claim.
There is **no relocation of any kind**, so `os88pkg.py` is a validator rather
than a generator. Both disks are standard FAT12 volumes (§19) that any host OS
mounts — and every byte read off one is still treated as hostile.

**Every image is built in FOUR geometries** — 1.44MB and 720KB (QEMU), 360KB
(86Box / a real XT) and 1.2MB 5.25" HD (§19, the AT-class machine with no 3.5"
drive). Changing the boot path, the FAT driver or the disk layout means
checking all four. This is the rule for the on-demand APPLICATION floppies too
— `zdisk`, `worddisk`, `cworddisk`, `paccmandisk`, `runcpmdisk`, `c64disk`,
`apple2disk`, `weavedisk`, `loomdisk`, `allapps` — which were three-geometry until 1.2MB
reached them.

**Twenty-five images, not nine.** The system and apps disks in four geometries
each, plus SIX more that exist at 360KB alone and ONE at 720KB alone -
`build/more720.img`, the 720KB apps disk's other half (SPEC.md 24.7), carrying
what that disk had to leave off - and the 128KB machine's two system disks,
`build/small360.img` and `build/small720.img` (kern_small, SPEC.md 24.5.7),
which `all` builds through `make small`'s sub-make. The small 720KB disk is
NOT the standard format: kern_small's two-sector FAT window refuses a
standard 720KB FAT, so it takes 2KB clusters, and that machine reads no other
720KB disk. And WIN16's own disk in four geometries, `win16*.img`
(§124.18.1), which left the apps disks when it outgrew them, and ARCADE's
release floppy in four, `arcrel*.img` (ARCADE-SPEC 1.6): the package and
`ARCADE.TXT`, no ROM.
`build/media360.img` —
`BEVERLY.MOD` is data rather than software and was 114 of a 360KB disk's 354
clusters before packages were compressed, so at that geometry it rides a disk
of its own (§24.4). **It is not on `apps360.img` as well any more, and cannot
be**: lz4-packed it is 42 clusters and that disk had no room for it.
**And `office360.img`, `network360.img`, `games360.img`, `emu360.img` and `util360.img` (§24.6)**, which
are the same pressure met with a shape that SCALES: 354 clusters is the
geometry that runs out first and this project keeps making applications, so
the answer is a disk per SUBJECT — one category of program at the ROOT of the
volume (no `APPS/` to click into when choosing the disk already said what you
came for), the documents those programs open in `MEDIA/`, a pre-made
`SYSTEM/APPDATA/`, and a warm `ASSOC.DAT` that costs nothing because
`os88disk.py` writes one for any packages it is handed. It is worth the three
disks for one measured line: `apps360.img` sat at **346 of 354 clusters,
eight spare**, and is at **313 of 354, forty-one spare** — *while* the 360KB
machine gained three more floppies of software. `apps360.img` is unchanged in
kind and is now **a curated selection** out of those three plus the packages
that live nowhere else — and §24.6.1 is the rule that matters about it:
**being curated onto it is a decision with a date on it**, remade every time
this geometry runs out, never a property of the package. At 360KB the module is a disk SWAP, which is what §24.4
was always for; `tests/lzship.py` carries both halves on one scratch image
because the harness cannot change a floppy under a running guest. Every other

**`THEWIRE.O88` is the exception to both halves of that** (§92): it is a
`SYSAPPS` package like `TASKMGR.O88`, so it lives in `SYSTEM/` on all FOUR
system-disk geometries and on **no** apps disk — a program whose whole subject
is fetching software off the network belongs on the disk the machine booted
from. `kern_small` leaves it off (`SMALLSYSAPPS`, derived from `SMALLOMIT`):
there is no NIC there, so there is nothing for it to refuse on.

**Adding a geometry is not only a table row**, and §19 carries what the 1.2MB
one cost: §18.93.1's boot canary sits at a fixed *file sector*, and the band of
sectors that cross a head is the **intersection** over every shipped disk — so
a fourth geometry made a canary nothing had touched inert on one disk of four,
which is precisely the fault it exists to catch. `tests/unit/t_canary.py`
caught it and `KSIG_OFF` moved. The gates that walk "every shipped image"
(`t_image`, `t_diskverify`, `t_canary`, `t_blobruns`) each hold their own list,
so a new image is not covered until it is in all four of them.
