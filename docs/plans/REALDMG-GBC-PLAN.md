# REALDMG-GBC-PLAN - Game Boy Color in RealDMG, with the Game Boy no slower

**Status: PLAN, nothing built** (written 2026-10-30 on `elendilon-next`; the
owner's answers to its five questions are section 10, and the sections before
already follow them).
RealDMG (docs/REALDMG-SPEC.md) runs the original Game Boy and refuses a
cartridge whose header byte 0143h is C0h, *"needs GB Color"* (REALDMG-SPEC
section 10). This plan is how it stops refusing.

The owner's words: *"the diffusion rom is A target but not 'the only' target
- GBC in general is. With the goal of keeping GB itself as fast - not losing
speed in the process of implementing GBC support."*

So there are two requirements and the second binds the first:

1. **Game Boy Color games in general** - the Color-only cartridges (C0h) and
   the dual ones (80h) - with `mowelan/gb-diffusion` as one named target
   (section 8), not the design centre.
2. **The DMG path loses nothing.** Not "a few percent for a good cause": the
   interpreter, the recompiler, the composer and the system code a DMG game
   runs through are measured before and after, and the answer has to be the
   same. Section 2 is how that is made true by construction rather than by
   care, and section 7 is how it is checked.

---

## 1. What a Color game needs that RealDMG does not have

Pan Docs' CGB chapters are the reference; this is the list, sized against
what RealDMG is today.

| feature | registers | what it is | RealDMG today |
|---|---|---|---|
| **WRAM banks** | `SVBK` FF70 | 32KB of work RAM: C000-CFFF fixed bank 0, D000-DFFF banks 1-7 | the view holds 8KB at C000-DFFF, read and written as plain memory (`mov dh,[ss:bx]`, section 3) |
| **VRAM bank 1** | `VBK` FF4F | a second 8KB at 8000-9FFF: 384 more tiles, and the BG map ATTRIBUTES (palette, tile bank, X/Y flip, priority) | one 8KB VRAM in the view; every store already leaves the fast path (`vr_wr`, 13.2.2), every read does not |
| **Colour palettes** | `BCPS/BCPD` FF68-69, `OCPS/OCPD` FF6A-6B | 8 BG + 8 OBJ palettes of four 15-bit colours, 128 bytes of palette RAM | four 2-bit shades and three palette registers |
| **Double speed** | `KEY1` FF4D + `STOP` | the CPU, DIV and the timers at 2x; the PPU, the APU and the frame at 1x | one clock: 114 M-cycles a line, 17,556 a frame, as constants (section 6) |
| **VRAM DMA** | `HDMA1-5` FF51-55 | general DMA (a copy of up to 2KB at once, the CPU halted) and HBlank DMA (16 bytes per HBlank) | OAM DMA only (FF46, a 160-byte copy at once) |
| **The PPU's Color rules** | LCDC bit 0, `OPRI` FF6C | LCDC.0 is BG-over-OBJ MASTER priority instead of BG enable; OBJ priority by OAM index, not X; OBJ tile bank and palette from the OAM attribute | the DMG rules (section 13) |
| **The rest** | `KEY0`, `RP` FF56, FF72-77 | DMG-compatibility switch (boot ROM only), infrared, undocumented scratch, PCM amplitude reads | FF4C-FF7F read FFh, writes dropped (section 9) |
| **Post-boot state** | - | A = 11h (the game's own Color test), and the CGB boot ROM's registers | the DMG boot ROM's (section 6.1) |
| **Bigger cartridges** | MBC5 | 1-8MB ROMs and 32-128KB RAM are common | ROM: fine since 10.3/10.3.1 (`RW_XROMMAX_KB` 8192). RAM: header codes 4 and 5 are kept as **four banks** (10.1) - a 64KB or 128KB cartridge RAM is 32KB here, which is a defect for those games on any Game Boy |

What is NOT on the list: the CPU. The SM83 is the same instruction set on
both machines, so every one of the core's handlers, the flag tables and
the recompiler's translator carry over as they are. Everything above is
memory map, registers, time and picture.

## 2. The rule that keeps the DMG as fast: a second BUILD, not a mode

**Every Color mechanism lives in code a DMG game never runs, and the choice
between the two is made once, at launch.** RealDMG already has the
indirections that make this cheap, which is why it is possible without
touching a hot path:

- **The core is generated** (`rdggen.py` writes `rdgcore.asm`) and shipped as
  PARTS 0 and 1 of the package (section 14). A second generation, with a
  flag, is a second core - `rdgcorec.asm` - with its own `read8`/`write8`
  and its own tails. **The DMG core is generated by the same code with the
  flag off and must come out byte-identical** (section 7.1).
- **The core leaves through far vectors** in the state block (`S_IORVEC`,
  `S_IOWVEC`, `S_MBCVEC`, `S_EVVEC`, section 5.2). A Color machine points
  them at Color handlers; the DMG handlers do not gain a test.
- **The composer is one call** (`rdg_render`, and the damage path's
  `ppu_dscan`/`rw_planes`, section 13). A Color composer is another routine,
  called instead.
- **The recompiler's templates are generated too** (`rdgtmpl.py`). The
  memory-access templates (`read8`/`write8`'s region tests, the direct
  `LD (nn),A` that starts at A000h, `rmw_lines`) get Color variants; the
  translator picks the set once per session.

**Recommended packaging: one source, two packages.** `REALDMG.O88` is built
as today; **`REALGBC.O88`** ("RealDMG Color") is the same source assembled
with `-DRDG_CGB`, carrying the Color core as its parts 0 and 1 and the Color
handlers, composer and templates in its image. The DMG package then cannot
contain a Color byte, so it cannot be slowed by one - and `cmp` is the
proof. The alternatives, and why not:

- **One package, Color as extra PARTS** (the core swapped at launch, the
  handlers dispatched by vector): nearly as fast, and one icon. But the
  package's own image - rdgsys, the composer, the writers - is shared, so
  every `%ifdef` becomes a run-time `cmp` somewhere in it, and "nothing in
  the DMG path moved" stops being checkable with `cmp` and becomes a
  routine-by-routine argument (`os88rdiff`). It also makes the DMG package
  larger on disks that are cluster-counted (`emu360.img`).
- **One package, a mode byte tested in the hot paths**: the obvious one, and
  the one the owner's rule forbids. A `cmp byte [ss:S_CGB],0 / jne` on
  every WRAM access is ~10 clocks on a 286 on the most frequent memory
  operation the Game Boy makes.

**What the user sees** (decided, section 10): `.GB` opens RealDMG and
`.GBC` opens RealGBC (the association, SPEC.md 54). **RealDMG given a C0h
cartridge hands the document on to RealGBC** - the user never sees a
refusal - and RealGBC given a DMG-only cartridge (0143h = 00h) hands it to
RealDMG. A DUAL cartridge (80h) runs in Color in RealGBC, and can still be
opened in RealDMG to run as a Game Boy, which is expected to be faster
(there is no Color machine under it at all); RealDMG's Machine > Load Game
keeps accepting 80h as it does today.

The rest of this plan describes the Color build. "The DMG build" is
REALDMG.O88 as it ships, and the gates in section 7 are what keep it so.

## 3. Memory

### 3.1 Where the Color state lives

The view (section 3) is full: 0000-3FFF is bank 0, 4000-7FFF is rdgsys's
(state block, flag tables, raster log, the composer's 4900-66FF, the bank
table at 6800h, `RDG_BUSE` at 6C00h, `S_JITXT`, `RDG_VMARK` at 7200h, the
save-state record at 7800h), 8000-FFFF is the Game Boy's. So the Color
build claims **one more block, `RDG_CGBSEG`**, at the load, holding:

| what | size |
|---|---|
| VRAM bank 1 | 8KB |
| WRAM banks 1-7 (the bank in D000-DFFF is ALSO in the view - 3.2) | 28KB |
| palette RAM, BG and OBJ, raw | 128 bytes |
| the composer's palette tables (3.4, section 5) | ~1KB |
| VRAM bank 1's damage marks (13.2.2's shape) | 512 bytes |

~38KB, a claim of the kind 14.4 already moves (`rw_mtab`). On a 640KB
machine it competes with the recompiler's 80KB and the bank cache's slots,
in the order `rw_load` already arbitrates (10.3); the plan's first measured
question is what a Color game gets there (G0, section 6).

### 3.2 WRAM banks: two designs, and the measurement decides

D000-DFFF is read and written as `[ss:bx]` by the core and by translated
code. Switching what is there is the question.

- **A. Copy on switch.** The view's D000-DFFF holds the CURRENT bank; an
  `SVBK` write (FF70 is above FF4C, so already a trip out to rdgsys) copies
  4KB out to `RDG_CGBSEG` and 4KB in. **Zero instructions added to any
  access**, the Color core's included. It is the shape cartridge RAM
  already has (`rdg_rammap`, 10.1: *"16KB moved, on a switch games make
  rarely"*). Cost per switch ~8KB of `rep movsw`: ~1.4 ms on a 12 MHz 286,
  ~20 ms on a 4.77 MHz 8088 (ESTIMATED from PERFORMANCE.md's 13.3 cycles a
  byte), plus the trip out.
- **B. A WRAMX segment in the Color core.** `read8`/`write8` in the Color
  core send D000-DFFF through a segment of its own, as ROMX goes through DS
  for 4000-7FFF (section 3): a switch is a pointer change. **Every C000-FFFF
  access in the Color core pays one more compare** (a `cmp bh,0D0h`-shaped
  test and an untaken branch) - and so does every WRAM template the
  recompiler emits.

A costs per SWITCH and B costs per ACCESS, so which one wins is a property
of the games and not of the design. **gb-diffusion is the adversarial case**:
it writes `SVBK` once per non-zero input of every layer, ~1,800 times a
diffusion step and ~29,000 a drawing, against ~160M M-cycles of work - A
adds ~40 s to a drawing on a 286 (ESTIMATED), which is real but not the
dominant cost (section 8). Most commercial Color games switch a few times a
frame or less. **G0 measures it on the owner's cartridges**, and the
recommendation going in is **A first** (it is small, it touches no
generated code, and it is correct), with B built only if G0 or G5 shows a
game that A makes slow. Either way it is the COLOR build's cost alone.

### 3.3 VRAM bank 1

**Stores already leave the fast path** (13.2.2: `write8`'s `cmp bh,0A0h`
sends 8000-9FFF to `vr_wr`, which marks the damage). The Color core's
`vr_wr` reads `VBK` and stores to the view (bank 0) or to `RDG_CGBSEG`
(bank 1), marking the bank's own map. **The view's 8000-9FFF stays bank 0
for good**, so the composer reads both banks from fixed places.

**Reads** do not leave the fast path on the DMG and must in the Color core:
with `VBK` = 1 a CPU read of 8000-9FFF has to come from bank 1. The Color
core's `read8` sends 8000-9FFF to the slow path always (a CPU read of VRAM
is rare - the hardware blocks it during mode 3 and games mostly write it);
G0 counts them to confirm. The copy idioms (`cpy_ff`, `cpc_ff`, `fill_ff`,
16.6) learn the bank in the Color core's tails.

### 3.4 Palette RAM

`BCPD`/`OCPD` writes (with `BCPS`'s auto-increment) go through rdgsys's
Color `rdg_iow` into `RDG_CGBSEG`, and mark the palette DIRTY for the
composer. A palette write is a picture change the VRAM marks cannot see, so
it is logged like the DMG's `BGP` writes are (the raster log, section 11):
a game that rewrites palettes mid-frame (a sky gradient, a fade) is drawn
by line, as SCX already is. G0 counts how many games do.

## 4. Time: double speed

**In double speed the CPU's M-cycle is half as long and the PPU's is not.**
RealDMG's clock is CPU M-cycles (section 6: `S_TNEXT - BP`), so:

- **DIV and the timers need nothing** - they are CPU-clocked on the
  hardware too, so counting in CPU M-cycles is already right.
- **The PPU and the frame double**: 228 M-cycles a line, 35,112 a frame.
  The Color core reads the line and frame lengths from the state block
  (`io_lcd`'s STAT/LY arithmetic, `S_TNF`), and the Color rdgsys schedules
  `S_TVBL`/`S_TSTAT` from them. The DMG build keeps its immediates.
- **The switch is a `STOP` with `KEY1` bit 0 set**, which already leaves the
  core (`RDGX_STOP`, section 5.1): the Color host toggles the speed, rescales
  the PPU's place in the frame and `S_TNEXT`, and resumes. Games switch once,
  at boot.
- **The host's budget is per FRAME**: `rdg_run`'s M-cycle budget and the
  package's pacing (15.2, 14) count frames, so a double-speed game simply
  spends twice the CPU per frame. That is the honest cost of a Color game
  and section 9 states it.
- **Sound**: the APU is not doubled (Pan Docs), so section 17's channel
  timing is taken off the PPU's clock in double speed, not the CPU's.

## 5. The picture

A Color composer, `rdg_renderc`, in its own include (`rdgppuc.inc`),
assembled only into the Color build. It keeps the DMG composer's
architecture - **a byte (eight pixels) at a time, never a pixel**, the
damage path, the raster log - and adds:

- **The attribute map** (VRAM bank 1 at the map's address): per tile its
  palette (0-7), its tile bank, X flip, Y flip and BG-to-OBJ priority. X flip
  is a 256-byte bit-reverse table; Y flip is the row index.
- **OBJ**: tile bank and palette from the OAM attribute (bits 3, 0-2);
  priority by OAM index (`OPRI` = 0, the Color default), not by X; LCDC.0
  as master priority.
- **Output: an INDEX, not a shade.** A pixel is palette x 4 + colour - BG
  0-31, OBJ 32-63 - which is exactly the 64 entries of palette RAM. What
  the index becomes is the writer's business, per display:

| display | what the index becomes | wave |
|---|---|---|
| **any, windowed** (Hercules, CGA, EGA, VGA) | the colour's LUMINANCE quantised to 2 bits, so the 5,760-byte two-plane buffer and every writer of section 13-15 take it unchanged | G3 |
| **VGA full screen** (mode 0Dh today, section 15) | 16 colours: the frame's 64 palette entries quantised to the 16 the mode has | G4 |
| **VGA full screen, 256 colours** | mode 13h's DAC loaded with the 64 palette entries themselves: **exact colour**, no quantisation; a mid-frame palette write is approximated by line | G4 |
| **VGA/EGA windowed in colour** | the desktop's 16 fixed colours, nearest by distance | G4 |

**Colour is the default wherever the display has it** (decided, section 10),
windowed and full screen. **Greys are an OPTION, offered only if they are
faster**: the grey arm reuses the DMG's two-plane buffer and writers, so it
is likely to be (a 2-bit plane pair against a 4-bit index per pixel through
the writer), but that is a G4 measurement - if colour costs no more, the
option is not shipped. On Hercules and CGA's mono modes greys are the only
picture and not an option.

The grey arm is still BUILT first (G3) because it makes every adapter run
Color games at once through writers that already exist; colour is then a
writer question and not a composer one, and G4 is what makes it the
default.

**What it costs the DMG**: nothing - `rdgppu.inc` is not edited. The tables
the Color composer needs (bit reverse, luminance, the palette's minterms)
are its own, in `RDG_CGBSEG`.

## 6. The waves

Each wave names its gate. Per the Testing rule (CLAUDE.md), waves verify on
the host and name the rows; the soak rows run once, after the last wave.

- **G0 - measure first, and pin the DMG baseline.**
  - A host-side counter for Color games, `gbprof`'s shape
    (`tools/gbprof.py` runs Peanut-GB, which has no Color): a pinned,
    fetched-never-committed Color reference (SameBoy, MIT, at a pinned
    commit) instrumented to count, per frame, `SVBK` and `VBK` writes, CPU
    reads of VRAM, palette writes, mid-frame palette writes, HDMA and GDMA,
    double-speed time, and the WRAM access mix. Run over the owner's Color
    cartridges and gb-diffusion; written to `docs/reports/`. It decides 3.2
    (A or B), 3.3 (slow-path VRAM reads) and 3.4 (palettes by line).
  - **The DMG baseline**, before a line of Color code: `rdgbench --vga` on
    `286-victory` (exact ticks, 13.3) for Super Mario Land and Kirby's
    Dream Land, gbclock on MartyPC's 5150, and the SHA-256 of the generated
    DMG core and templates. Those are the numbers section 7 holds.
- **G1 - the split.** `rdggen.py` and `rdgtmpl.py` take a Color flag;
  `-DRDG_CGB` builds REALGBC.O88 with the Color core as its parts. Nothing
  Color in it yet but the header check: it accepts C0h and 80h. **Gate: the
  DMG core, templates and REALDMG.O88 are byte-identical to G0's**
  (7.1).
- **G2 - the machine.** `RDG_CGBSEG`; WRAM banks (3.2, A); VRAM bank 1
  (3.3); the Color post-boot state; `KEY1`/`STOP` and the double-speed time
  base (section 4); the register set (`OPRI`, `RP` reading "no light",
  FF72-77, `PCM12`/`PCM34`); GDMA, and HBlank DMA on the line event
  (6.3's per-line mechanism, armed only while one is running). **Gate**:
  blargg's `cpu_instrs` and `instr_timing` in Color mode at both speeds on
  the bare harness (12.1), and Mooneye's Color-specific acceptance tests,
  each fetched by `tools/getgbtest.py` at a pinned SHA-256.
- **G3 - the grey picture.** `rdg_renderc` (section 5) into the existing
  two-plane buffer, with the damage path. **Gate**: `cgb-acid2` (Matt
  Currie, MIT) against its reference image reduced to the same luminance
  quantisation, and `gbdamage`'s shape over a Color game (damage against
  whole frames, 0 differing).
- **G4 - colour, the default.** Full screen 256 colours (exact) and 16
  colours, and windowed colour on VGA/EGA. Then the measurement that decides
  the grey OPTION: `rdgbench`'s shape on a Color game, colour against grey,
  windowed and full screen, on `286-victory`; the Machine menu item ships
  only if grey is measurably faster (section 5). **Gate**: `cgb-acid2` exact
  in mode 13h.
- **G5 - the recompiler.** Color templates (WRAM per 3.2's choice, VRAM
  writes, the copy idioms' bank), chosen once per session; Static mode's
  table (16.8). **Gate**: `gbcpu`/`gbaot`'s legs run in Color mode
  translated and interpreted, identical frame for frame; G0's games
  measured both ways. If G0 found a game that design A makes slow, B is
  built here.
- **G6 - the package.** The `.GBC` association (RealGBC's) and the two
  hand-offs (section 2); cartridge RAM up to 128KB (fixing 10.1's four-bank cap - a DMG-side
  defect too, and the one change in this plan that touches the DMG build,
  in cold load code only); save states with the Color fields, VRAM bank 1,
  WRAM banks and palette RAM (10.4, a format version bump); the log's head
  saying Color and the speed; the Guide manual and the Wire listing.
- **G7 - gb-diffusion and the big cartridges.** Section 8. **Gate**: a
  doodle drawn on kern_mega (Bochs for correctness, 86Box's `286-mega` for a
  time), compared with the reference emulator's state after each step as
  the project's own `test_rom.py` does.

- **T - trimmed cartridges, for the DMG too, and independent of every
  Color wave** (decided, section 10). Two halves:
  - **A file shorter than its header** is accepted when it is a whole
    number of 16KB banks: the banks past its end are not stored at all and
    read FFh, which is what a real cartridge's unpopulated ROM answers. The
    memory a cartridge takes becomes the FILE's size, so a 2MB cartridge
    trimmed to its 76 real banks needs 1.2MB, in one claim, the bank cache
    or kern_mega's place alike.
  - **A full-size file whose tail is FFh** gets the same saving without
    anyone trimming it: the load already reads every bank (`rw_bload`,
    `rw_bread`), so a bank that is all FFh is noted and not stored, and
    every such bank's table entry names ONE shared FFh bank. Most such
    padding is at the end, so the stores keep their bank-n-at-n layout
    and simply stop early; a hole in the middle shares the FFh bank
    through the table.
  - What it touches is LOAD code: `rw_plan`'s size (the file's, not the
    header's), `rw_bload` and the one-claim read, `rw_xfill`/`rw_pmfill`
    and `rw_bfill`'s table, and `rw_hdrchk`'s size compare - none of it a
    path a frame runs through (7.3, judged with `os88rdiff`), and
    `S_BMASK` stays the header's so a game's bank arithmetic is unchanged.
  - The owner's example is Looney Tunes, a "1MB" cartridge more than half
    empty by their account (not measured here: no cartridge is in the
    tree); gb-diffusion is 76 banks of 128. **Gate**: `gbbank`'s cartridge
    built trimmed and with an FFh tail, every bank still checking right,
    and the claim's size read off the machine against the file's.

**Not in this plan**: the full static recompiler for Color cartridges
(section 20's `gbaot.py` refuses a C0h game until a wave says otherwise),
DMG games in the CGB's compatibility palettes, the link cable and infrared,
and kern_small (a 128KB machine cannot hold a Color game's 38KB beside the
core's 128KB carve; REALGBC rides only the disks RealDMG rides, and if a
small disk ever carries one it is an omission with that reason, SPEC.md
24.5).

## 7. The DMG speed gates

**The owner's requirement is a measurement, so it is gated as one.**

- **7.1 Byte identity, host-side, every build of the Color work.** The
  generated DMG core (`rdgcore.asm` and its assembled parts), the DMG
  templates and `REALDMG.O88` itself are compared against hashes pinned in
  a file beside the soak row (`tests/rdgdmgsame.txt`). Any difference
  fails the row and names the artefact. A DMG change that is MEANT (a fix,
  G6's RAM banks) updates the pin in the same diff, which makes it a
  decision someone reads rather than a drift - `tools/abi.lock.json`'s
  shape. It belongs in `soak` (it is about one package, docs/WRITING-TESTS.md
  2.1) and is run after every Color wave's last commit.
- **7.2 The clock, after the last wave.** G0's `rdgbench --vga` figures on
  `286-victory` and gbclock on MartyPC are taken again and must match to the
  tick (`rdgbench` is exact: *"the same build gives the same ticks"*, 13.3).
  Where 7.1 holds, 7.2 cannot differ, so 7.2 is the check that 7.1 is
  checking the right things.
- **7.3 What may change in the DMG package, and how it is judged.** G6's
  cartridge RAM and the hand-off toast are DMG-package code, at LOAD time.
  They are allowed, and judged with `tools/os88rdiff.py`: no routine a
  frame runs through moves, and none moves by an odd amount (PERFORMANCE.md
  Part 7's parity rule).

## 8. gb-diffusion

`mowelan/gb-diffusion` (MIT), `docs/gb-diffusion-28x28.gbc`: a 1.08M-
parameter MLP that draws a 28x28 Quick, Draw! doodle in 16 DDIM steps, ~85 s
a drawing on a real Game Boy Color. What it asks of this plan, from its
header and `rom/main.asm`:

- **0143h = C0h**, and it halts on anything but A = 11h at boot.
- **Double speed** (`KEY1` + `STOP` at boot).
- **WRAM banks 1-7**: a 24KB product table in banks 1-6 built at boot (the
  CPU has no multiply), bank 7 the canvas, header and footer. `SVBK` is
  written per non-zero input in the multiply-accumulate loop: section 3.2's
  adversarial case.
- **VRAM bank 1**: the canvas double-buffered across the two banks, picked
  by the BG map's attribute bank bit and LCDC bit 3.
- **GDMA**: three 768-byte transfers to refresh the canvas, and one for the
  header and footer.
- **Two BG palettes** written once.
- **MBC5, 2MB, no RAM** - of whose 128 banks only 76 hold data (1.19MB); the
  rest is FFh padding. On kern_mega since 2026-10-30 it needs ~2MB of the
  extended pool in place (REALDMG-SPEC 10.3.1), so a 3MB machine is tight;
  wave T makes it 1.2MB, trimmed or not.

**What to expect, ESTIMATED**: the work is ~160M CPU M-cycles a drawing in
double speed. RealDMG runs DMG games at about real speed on a 12 MHz 286
with the recompiler (16.6), and this loop is the recompiler's best case (an
unrolled straight line of loads and adds). Double speed alone halves the
speed relative to a real Color, so **a few minutes a drawing on a 286**, and
nearer real time on a 386. No measurement exists; G7 takes one.

## 9. What a Color game costs, stated honestly

- **Double-speed games are twice the CPU** of a DMG game per frame, before
  anything else. On a 286 that is roughly half speed for those games; a 386
  is the machine for them. Single-speed Color games cost the DMG's CPU plus
  the Color composer.
- **The composer costs more per line**: attribute fetches, flips and a
  palette per tile, where the DMG's is one palette for the line.
- **Memory**: ~38KB more conventional heap (3.1), and Color cartridges are
  bigger, so most want the bank cache (10.3) or kern_mega's in-place store
  (10.3.1).
- **Disk**: REALGBC.O88 is a second package, roughly REALDMG.O88's size
  again. Which disks carry it is a G6 question against the cluster counts
  (`emu360.img` is where RealDMG lives at 360KB).

## 10. The owner's decisions (2026-10-30)

1. **Hand it on.** RealDMG given a C0h cartridge hands the document to
   RealGBC, and `.GBC` becomes RealGBC's association (section 2).
2. **Dual cartridges (80h) are RealGBC's**, in Color - and can still be
   loaded in RealDMG as a Game Boy, for the speed that is expected to buy.
3. **Colour**, with an option to fall back to greys **only if that is a
   speed benefit** - which G4 measures before the option ships (section 5).
4. **Two packages for the initial plan** (section 2). To be reconsidered
   when it is built, against what one package would actually cost in speed
   and in package size - so G1 records both packages' sizes, and G5's
   measurements are the input to that reconsideration.
5. **Trim: yes**, because what it buys is memory - a "2MB" cartridge that
   is mostly padding stops taking 2MB. It is wave T, and it reaches DMG
   cartridges too (Looney Tunes, the owner's example), so it does not wait
   for the Color work.
