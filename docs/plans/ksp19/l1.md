# Kernel size pass 19 - `l1`: the image pad, without the flag day

Agent `l1`, branch `ksp19-l1`, cut from `kernel-size-19` at `174b80bf`.
Row: **L1** (ABI-BREAK-LIST L and 13.1, LAST-DROP-BYTES 7.13), with the
owner's answer 4 - design kern_small's fill first, take L1 only on a design
where kern_small comes out neutral or better.

## Summary

The flag-day form of L1 fails the owner's test on kern_small, so it was NOT
built. Its whole saving - the image's 512-byte rounding pad - was taken
instead with **no ABI change at all**, on every kernel, kern_small included:

* The pad exists because guard 6 made `FAT_SEG` and `LOW_SEG` (whose first
  512 bytes are `dsk_secbuf`) multiples of 32 paragraphs. What int 13h
  actually refuses is a transfer that STRADDLES a 64KB physical page (09h).
  A 512-byte base is the way to rule that out for a base nobody knows until
  run time (`HEAP_SEG`, every claim, `KERNEL_SEG`'s boot reads) - and those
  keep it. The FAT window and `dsk_secbuf` are assembly-time CONSTANTS, so
  guard 6 now proves the fact itself: each lies inside one 64KB page.
* So `KIMG_PARA` rounds `.text` + `.bss` to the paragraph (kern_mega: to its
  128-byte selector granule, because `FAT_SEG`/`LOW_SEG` are identity
  selectors there, GDT base i x 128). `KERNEL_SEG` stays 0x0060; no package,
  driver, DOS, boot path, ROM, `COLDHMA.SYS` or host tool changes.
* On the `LADDER_PACK` kernels (big, small, emu) `KERN_END` is now the ONE
  rounding in the ladder - L1's stated end state.

## TAKEN

**L1's saving, no-ABI form** (`kernel/kernel.asm` KIMG_PARA + guard 6;
comments in `kernel/dskwin.inc`; `tools/kernsize.py` reports the packed
kernels as one rung, KERNEL_SEG..KERN_END, with the FAT window a member).
MEASURED with `tools/kernsize.py --json` at this tree, base vs. new,
paragraph-exact ladder sum:

| kernel | `.text`+`.bss` | KIMG_PARA | ladder bytes | KERN_SIZE |
|---|---:|---:|---:|---:|
| kern_big | 45,354 | 2,848 -> 2,835 | **-208** | 96,256 (unchanged: the top rung absorbs it, 23 -> 231 slack) |
| kern_small | 32,628 | 2,048 -> 2,040 | **-128** | 58,368 (unchanged) |
| kern_emu | 45,600 | 2,880 -> 2,850 | **-480** | 96,768 (unchanged) |
| kern_mega | 51,144 | 3,200 -> 3,200 | **0** | unchanged - its 56-byte pad sits inside the 128-byte granule at this build; every kernsize figure is identical, so its kernel is the same binary |

Bytes, not rungs: these are the bytes every later byte of `.text`/`.bss` now
lands in before any rung is billed, exactly as L1 would have given. The pad
varies 0-511 a build (0-127 on kern_mega). Code bytes: 0 (`.text` and `.cold`
unchanged; only segment VALUES moved). Packages: 0 bytes, none rebuilt for it.

## REFUSED / NOT BUILT

**L1 as written (KERNEL_SEG 0x0060 -> 0x01A0, FAT + `dsk_secbuf` below the
image).** kern_small's design, measured off `build/smallk/kernel.map`: the
ten-sector region below a shared 0x01A0 is 5,120 bytes; kern_small's natural
content for it is FAT 1,024 + `.lowbss` 2,868 (`dsk_secbuf` included) + task
0's stack 512 = 4,404, a **716-byte hole** against a 140-byte pad -> **+576
bytes** (0x24 paragraphs: KERN_END raw 0xE97 -> 0xEBB). No fixed-size fill
exists: what is left to move is `.bss` reached through DS (the window table
`wm_wins` 390, `ico_stage` 256 read by `icon_draw` through DS:SI,
`inst_tab` 192 with 51 sites, `wm_clip_tab` 128 with 17...), which would cost
an `ss:` byte a site on kern_small only plus string-op segment juggling, or a
second cold segment for ~700 bytes of `.cold`, which is the "if it fits, put
it here" shape LAST-DROP 7.13 refuses. No shared `KERNEL_SEG` helps either:
kern_big needs ten sectors under its image to lose its pad and kern_small
has 3,584 bytes less to put there. Superseded anyway by the form above, which
gives kern_small -128 instead of +576 and kern_big the same -208.

**kern_mega's ladder packing** (owner's question): not taken. At this build it
buys **0**: the image 51,144 and LOW 6,112 (`.lowbss` 5,600 + 512) already
round to 51,200 and 6,144 under the 128-byte granule exactly as under 512.
Packing LOW/COLD/MEGA to the granule would be worth ~64 bytes a rung on
average and needs the switch-time heap-floor drop onto `COLD_RAM` to round to
512 itself; recorded, not priced further.
