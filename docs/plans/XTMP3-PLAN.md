# XTMP3 — delivery plan

An MP3 player that plays every file at the best quality the machine can
sustain and is honest about which quality that is. It runs from a 486 at
the source's own rate down to a 4.77 MHz 8088. The 8088 decodes the whole
track to a hard-drive WAV first, then plays it. The binding contract is
SPEC.md §121; the owner's brief is `docs/xtmp3/design/PROMPT.txt`; the diary is
[HOW-XTMP3-WAS-BUILT.md](../HOW-XTMP3-WAS-BUILT.md).

## Delivery stories

Each story is a reviewable commit (or a merge of a track branch) on
`feature/xtmp3`, pushed to the one draft PR. A box is ticked only when the
story's own verification has been run and its evidence is in the PR.

- [x] **S0 Foundation.** Worktree, the mockups in `docs/xtmp3/design/`, SPEC
  §121 pinned, this plan, the diary, the draft PR.
- [x] **S1 Reference decoder (host).** `tools/x3sim.py` decodes every
  fixture: MPEG-1/2/2.5, mono/stereo/joint (M/S, intensity), CBR/VBR, short
  and mixed blocks, reservoir reach-back, at 8 to 320 kbps. Its STANDARD
  integer model matches `lame --decode` within the documented SNR and peak
  bounds. Truncated and malformed fixtures are refused or recovered as
  §121.2 says, never read past. The Q-format table is written in its
  docstring. Fixtures are generated by `tools/x3fixtures.py` and committed
  with their recipes and hashes.
- [ ] **S2 Device formats.** `SOUND.DRV` gains 16-bit and stereo streams
  on the DSPs that have them (SB Pro: 8-bit stereo; SB16: 16-bit stereo,
  DMA 5), as new open flags and a new caps bit, with the 8-bit mono ABI
  untouched. Driven on QEMU's SB16 and on 86Box; a new §34.5 subsection written. *(OS
  integration the brief allows: "add a small reusable integration".)*
  *Status: verified on QEMU's SB16 (`sndfmt`, 46 checks) and MartyPC's DSP
  2.01 (`sndfmtmarty`); the SB Pro path has not been heard on 86Box.*
- [x] **S3 XT approximation study (host).** The product-table designs of
  the brief's §5 to §9 are built and MEASURED on the host. That covers
  coefficient-major rows, 8-bit and 10-bit codes, a companded code map, and
  16/8/4-term synthesis with the terms chosen per phase by error. Also the
  quarter-square table (isolated, off by default) and shift-add constants.
  Each approximation gets SNR, peak error, DC, clip count, an aliasing and
  transient check, and a WAV for listening (`docs/xtmp3/listen/`). An
  8088 cycle model of each kernel includes its addressing. The output is the
  XT profiles' definition and `tools/x3tables.py`'s XT packs.
- [x] **S4 The face.** `XTMP3.O88` opens with the mockups' face on VGA (FULL),
  EGA and Hercules (MID) and CGA (COMPACT), in colour and black and white,
  every element cached. The art comes from `tools/os88x3art.py`: codex-made
  masters for the knob, the VU dial and the wordmark, derived
  deterministically, plus generated fonts (LCD caps, panel small caps, two
  seven-segment sets, the dial digits). Menus, keys, About, the queue, Open
  and the `.MP3` association all work on a demo state. The identity check
  (incremental equals full paint) passes on each layout.
- [x] **S5 Parser on target.** The shared `x3pars.inc` covers frame sync, ID3
  skip and title, Xing/Info/VBRI duration, side info and the reservoir, and
  it is byte-identical in decision to `x3sim.py`'s parser on every fixture.
  The queue shows real titles and durations.
- [ ] **S6 STANDARD decoder on target.** `x3std.asm` is BIT-EXACT to
  `x3sim.py`'s STANDARD model at divisors 1, 2 and 4, proved by a bench
  build that decodes each fixture to a WAV on QEMU and is compared on the
  host. Real-time playback through the SB stream with the worker and the
  look-ahead ring, and Original on 16-bit stereo where S2 offers it.
  *Status: the bit-exact half is verified (`x3stdexact`, 157 of 157); live
  Original in 16-bit stereo runs on QEMU's SB16 with the real part
  (`docs/xtmp3/s10-live-stereo.png`), and has not yet been listened to.*
- [x] **S7 XT backend on target.** `x3xt.asm` with table packs expanded at
  OPEN and CRC-checked, bit-exact to `x3sim.py`'s XT model. Speed is measured
  per profile and per stage on MartyPC's 5150 (cycles, not wall time), and
  the peak working set is within 400,000 bytes.
- [ ] **S8 The ladder.** Calibration is bounded and timed by `pit_now`,
  includes the feed and the disk, and the cache is keyed per §121.5. Step-
  down happens at a safe boundary with hysteresis, and an override stays
  visible. Deterministic fixtures exercise each transition: a capable
  machine stays on Original, a middling one halves before any XT rung, and
  an XT goes to Decode first. The ladder is measured on 86Box 286/386/486
  and MartyPC.
  *Status: every transition is verified over the stub backend (`xtmp3eng`'s
  `ladder` and `slowdown`), and MartyPC's VGA XT takes the shipped package
  to Decode first with XT Standard (the guide's capture). The measurements
  on 86Box and MartyPC are FIELD's (SPEC §121.11.5).*
- [ ] **S9 Decode first.** The drive dialog covers multiple fixed volumes,
  read-only volumes, no hard drive and too little space. Then the Save
  dialog, the disk estimate, conversion with progress, measured speed and
  responsive Cancel, finalisation (trim, lengths, verify, rename), cache
  identity and reuse, stale and incomplete rejection, and Decoded Files.
  The finished WAV plays through the SB, the speaker or the Covox with no
  MP3 work.
  *Status: verified by `xtmp3eng`'s legs except a read-only volume, the
  Decoded Files delete, batch approval over two tracks, and the speaker's
  and the Covox's sound (QEMU checked their state only).*
- [ ] **S10 Acceptance.** Docs: the guide manual, §121.11 measured, a
  PERFORMANCE set, the INDEX, and the diary with pictures. Suite rows,
  disks, a 86Box machine profile, and the screenshots on every adapter.
  Then the deduplicated soak union once and `test-full` once.
  *Status: SPEC §121 rewritten as shipped with §121.12's disk placement;
  the guide manual and song pages; the disks (`make xtmp3disk`, the music
  disk, the 1.44MB and 1.2MB apps disks, the live media); INDEX, README and
  the screenshots in `docs/xtmp3/s10-*.png` (the docs track). Open: §121.11's
  period-machine rows (FIELD), a PERFORMANCE set, suite rows for the face,
  the soak union and `test-full`.*

## How the work is fanned out

The owner asked for the work to be parallelised. The tracks are cut so that
no two agents edit the same file, and each works in its own worktree on its
own branch off `feature/xtmp3`:

| phase | track | worktree / branch | stories | depends on |
|---|---|---|---|---|
| 1 | **numerics**: reference decoder, fixtures, harness | `os8088-x3num` / `xtmp3/numerics` | S1 | - |
| 1 | **device**: SOUND.DRV 16-bit/stereo | `os8088-x3snd` / `xtmp3/sound` | S2 | - |
| 1 | **xt-study**: product tables and approximations | `os8088-x3xts` / `xtmp3/xtstudy` | S3 | - (analysis filterbank fixtures of its own; joins S1's model in phase 2) |
| 1 | **face**: art, drawing layer, package skeleton | `os8088-x3face` / `xtmp3/face` | S4 | - |
| 2 | **front end + STANDARD** on target, the bench | `os8088-x3std` / `xtmp3/std` | S5, S6 (bit-exact) | S1, S4 |
| 2 | **XT backend** on target | `os8088-x3xt` / `xtmp3/xt` | S7 | S1, S3, S4; the record contract from `xtmp3/std` |
| 2 | **engine plumbing**: worker, rings, feed, the drive dialog, conversion, finalisation, cache, finished-WAV playback, over a stub backend | `os8088-x3eng` / `xtmp3/eng` | S9, the plumbing of S6 and S8 | S2, S4; the record contract from `xtmp3/std` |
| 3 | **integration**: the real backends behind the engine, calibration and the ladder, live playback | `feature/xtmp3` (or one agent) | S6 live, S8 | phase 2 |
| 4 | **acceptance** | `feature/xtmp3` | S10 | all |

The integrator (the session that owns the PR) merges each track branch
into `feature/xtmp3` when its story verifies, folds the track's contract notes
into SPEC §121, ticks the box and updates the PR body. Agents do not merge,
push to the PR branch, or run soak rows or `test-full` (CLAUDE.md, *Testing*):
they verify on the host, with `make`, by looking at a boot, and name the
`tests/suite.py` rows their story needs.

## Decisions taken (the owner may overrule any)

1. **The colour design is the attached teal-desktop mockup**
   (`xtmp3-color.png`), whose layout is the monochrome mockup's. The
   package's own colour concept (`xtmp3-color-alt.png`) uses a different
   arrangement and is kept for reference only. The desktop colour, the menu
   bar and the window's title bar are the OS's own chrome and are not drawn
   by the package.
2. **Assembly, not C.** The decoder needs 32-bit accumulators. The C dialect
   has no `long` (§73), and the SDK does not wrap the stream verbs for C
   (§86's reason).
3. **Tables ship as generator input and are expanded at OPEN** (§121.10). A
   floppy read of the full XT pack would cost an XT more than ten seconds.
   The host generator still writes the identical bytes and the CRC.
4. **The finished file is a standard WAV** (PCM, with an `xtm3` identity
   chunk). The Audio Player and any host can play it, and the PC speaker and
   Covox play it through §86.21's bracket. On a speaker-only machine, MP3 is
   never decoded live.
5. **The meters do not fake stereo.** With mono output the right dial is the
   BUFFER gauge (§121.8).
6. **16-bit/stereo output is an OS integration in this PR (S2)**, not a
   package hack. If the owner would rather not grow SOUND.DRV, S2 is dropped,
   and Original plays at the source rate in 8-bit mono with the device limit
   shown.
7. **Fixtures are ours.** The signals are synthesized by `tools/x3fixtures.py`
   (tones, sweeps, chords, bass, transients, noise bursts, silence, and three
   short generated "songs" named after the mockup's queue). They are encoded
   with the host's LAME, which is used as a tool and never vendored. The
   decode reference is `lame --decode` (mpglib). No third-party audio is
   committed.
8. **No 8087**, anywhere (the brief's §0).

## Existing facilities reused (docs/INDEX.md was read first)

| need | the OS's answer |
|---|---|
| PCM out, any card | `OSAPI_SND_STREAM` ring verbs (§34.5), the Audio Player's worker/feed/refill handshake (§86.5) |
| no card | §86.21's speaker bracket (`apps/os88spk.inc`, §34.11.9's shaper) and the Covox tier (§34.14), on a FINISHED file only |
| code beyond 64 KB | package PARTS (§20.12): the two backends as `OP_LAZY` `OP_SEG` parts, `op_fetch`/`op_drop` |
| memory | `OSAPI_MEM_CLAIM`/`AVAIL`, the carve; `OSAPI_SYS_KB` for the report |
| streaming reads | `os88_rseq` over `OSAPI_FILE_READ_SEQ` (§18.4.8.1) |
| streaming writes | `OSAPI_FILE_WRITE_SEQ` (§18.4.9); `OSAPI_FILE_WRITE_AT` for the header; `OSAPI_FILE_RENAME` |
| volumes | `OSAPI_VOL_KIND` (fixed vs removable), `OSAPI_FILE_GOTO_QM` + `OSAPI_VOL_STAT` for free space |
| folder and name | `OSAPI_FILE_DLG` Save (§38) |
| worker may not touch files | the FTPD/Audio handshake: the worker stages, `OSAPI_WM_ONWAKE` commits (§20.6 rule 7) |
| timing | `apps/os88pit.inc`'s `pit_now` |
| a retro hardware face | the retro-face skill: CDRack's `crdraw.inc`/`crface.inc` shape, `tools/os88cdart.py`'s generator shape |
| buttons, About, scroll bar | `apps/os88ui.inc` (`OS88UI_BOWN`, `OS88UI_ABOUT`, `OS88UI_SCROLL`) |

| settings and the cache index | `apps/os88data.inc` (`SYSTEM\APPDATA`) |

| volume | the mixer verbs (§34.15, `SND_CAP_MIXER`) |

## Verification discipline

During the tracks: assemble with `cpu 8086` and `-w+error`, then `make` (the
fast tier), `make KERN_SMALL=1` if the package ships there, host model checks,
and a boot to LOOK, cropped and zoomed. XT numbers come from MartyPC's cycle
counter and never from QEMU's wall time. 286/386/486 numbers come from
86Box, driven by an `\AUTOSTRT` bench that writes its report to the disk.
Each track names its suite rows. After the last merge: the deduplicated soak
union once, then `test-full` once. A failure re-runs only what failed.
