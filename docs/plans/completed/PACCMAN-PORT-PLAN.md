# The PACCMAN port plan

The design record of `apps/paccman/` (SPEC.md §91), a C port of Andre Weissflog's
`pacman.c` (https://github.com/floooh/pacman.c, MIT), drafted by the
`port-to-os8088` skill's scouting workflow on 2026-09-06 from the reference
source and this tree, reviewed through three adversarial lenses and reconciled.
SPEC.md §91 is the contract; this file is why it reads that way, wave by wave.
Every wave of `workflows/implement.js` reads it. The reference commit is
**0f5ec5a**; the reference lives outside this repo (nothing is vendored,
CONTRIBUTING.md §6) and `tools/paccman_assets.py` is what turns its tables into
`apps/paccman/pmc_rom.c`.

## Decisions

Taken on the plan's recommendations on 2026-09-06 (the user's instruction was
the port itself: "Use the C toolchain to port this C99 version of pacman as a
second option for the game. Call it PaccMan. Maybe this port is more
performant on XTs."):

- **Q.** Carry the Namco arcade ROM dumps (tiles, sprites, hardware colours, palette) and the emulator-captured sound register dumps into the shipped package, as the reference embeds them under its MIT licence?
  **Decision:** Yes.
  **Why:** They ARE the arcade look and sound the user asked for, the reference ships them the same way, and the tree has a user-decided precedent for shipping third-party ROM data (apps/c64/rom/, C64-SPEC). Without them this is not an arcade-faithful port. LESSONS.md 1: the licence question is the user's, asked once, early

- **Q.** The content the reference itself lacks - the attract-mode chase, the coffee-break intermissions, the per-round speed and dot-limit table (all listed as missing in pacman.c's own header, lines 50-54): port what the source has and state the gaps, or implement them from the Pac-Man Dossier?
  **Decision:** Port what the source has.
  **Why:** Adding arcade content the reference does not carry is new game design rather than a port, it cannot be traced to a source file the way every other surface here is, and the speed table alone would make the port diverge from its reference in exactly the behaviour tests/paccman.py fixes by fixture

- **Name:** package `PACCMAN`, directory `apps/paccman/`, images `build/paccman*.img`, `make paccman` / `make paccmandisk`, vm `vm/xt-paccman`. Shares nothing with `apps/pacman` (SPEC.md §73.12's rule).
- **Agents:** the implementation waves run on Opus 5 for every role, the C64 port's mix.

## Summary

PACCMAN is a second Pac-Man for os8088, beside the shipped assembly PACMAN (SPEC.md 89, the Roklan/Atari disk port): a C reimplementation of Andre Weissflog's arcade-faithful pacman.c (MIT, 2020; the tables and behaviour are taken from commit 0f5ec5a of github.com/floooh/pacman.c, 2 Jul 2026, and that hash is pinned in the extractor and printed in pmc_rom.c's header, README and the About card) - the 28x36-tile 224x288 vertical arcade field held as video_ram/color_ram exactly as the Namco board holds it, the real tile/sprite/colour ROM tables, the four ghost personalities with the Dossier's scatter/chase schedule, the ghost-house dot counters, the 21-row fruit/fright level table, the CHARACTER/NICKNAME intro reveal, and the arcade's three-voice register-driven sound reduced to the one PC-speaker voice with the fact stated. Nothing is shared with apps/pacman (name, dir, images, targets, vm dir, source) per SPEC 73.12's rule. The reference is a reimplementation, not a compile: everything sokol (window, GPU tile renderer, WSG synth, nanosecond timing) is replaced; uint32 ticks become two-word triggers, the 59 by-value int2_t sites become packed tile ints and parallel pixel arrays, the score becomes BCD digits, the levelspec by-value return becomes three const arrays; the gameplay, tables, strings and timings port line for line. Input keeps the reference's LEVEL semantics (input_dir reads held state every tick; there is no buffered turn in pacman.c) with ONE stated divergence: because a frame here is 55-200 ms rather than 16, a key PRESS is latched until the next frame's poll so a tap shorter than a frame is not lost. The rendering keeps the Atari port's PROVEN shape (one worker sleeping to a tick deadline, dirty 8-row tile bands composed in the package's RAM by assembly inner loops and sent with ONE blit per band, 1bpp packed bands on mono, alternate-row sampling where the display is short) but drops the 28 KB persistent canvas for an 896-byte band scratch (the dirty span is exactly the set of tiles that must be recomposed anyway) and, on colour displays, sends each band through OSAPI_GFX_BLITP (four planes, ~114 us a row-plane + ~4 us a byte, PERFORMANCE.md 10040-10065) instead of GFX_BLIT4, which at 224 px wide always takes kernel/vga12.inc:2723's planar decoder at ~106.9 cycles a pixel (~41 ms per 8-row band, ~2 fps for a 12-band frame). BLITP is the ONE lever that could make the user's 'more performant on XTs' true, and the plan carries NO fps prediction for it: the blit is only one of four costs (tile/sprite composition, the packed-to-planar repack and the C game logic are the other three, and LESSONS.md 13 records a first per-cell guess being 7x wrong), so wave 1 brackets all four on MartyPC's XT profile with a band bench (tests/pmcbandbench, rcbandbench's shape) and the harness's cost table is priced from those measured terms; the hypothesis has an explicit verdict (PACCMAN.O88's fps >= PACMAN.O88's on the same MartyPC profile, both measured by the same bracket in wave 4). Tick posture is a fact and a decision the plan takes: 60 Hz arcade ticks run as an accumulator of 3.3 game ticks per elapsed 18.2 Hz OS tick, capped at PMC_CATCHUP_MAX = 2 OS ticks' worth per drawn frame (every sprite stays within one tile of where it was last drawn, the slowdown is halved against a fixed cadence), the worker re-anchoring rather than bursting; the effective game speed per adapter is measured and stated, never predicted. Estimated ~34.5 KB image (cword's measured ~9.4 bytes per non-comment code line) + 5 KB bss = ~39.5 KB of 61,440, so no overlay is planned and the split line (intro, round setup, About) is named for the day os88pkg's line passes 50,000. The worker declares OS88_STACK_256 - a 384 request can be REFUSED outright when frotz/browser/ftpd hold both 384 slices (os88api.inc 2057: 'the smallest free slice that is at least that big, or refuses') and a refused spawn is a game that never runs - so the tick path's call chain is flattened to fit it and MEASURED with tools/stkdepth.py and stkwater.py in wave 2, with the water mark asserted in tests/paccman.py. The window needs WF_KEEPH: the 307-row frame hangs 1-3 rows over the dock on EGA/Hercules and the CGA half-height frame 7, both under SPEC 11.93's DOCK_H/2 line, so every adapter gets all 36 tile rows without a WM_PREFER thunk. Nothing is greyed: every machine this kernel boots on has a PC speaker (kernel/snd.inc:755 answers a constant), so Game > Sound On/Off is a plain toggle. The 86Box machine is vm/xt-paccman (LESSONS.md 9's objection - an XT target before a measurement is a claim - is answered by the MartyPC measurement in the port's own gate).

### Absent

- (AMENDED AT WAVE 1'S REVIEW) Pause and Sound ARE greyed while the build has no game in it, and the fact is the BUILD rather than the machine: there is no tick loop until wave 2, so pmc_paused is a byte nothing reads, and pmc_snd.c is a wave-3 stub, so there is no sound code in the image at all. A control that changes its own label and nothing else is worse than one that says why it cannot act, so both carry MENU_DIS and the same reason - '(No Game)' - and the wave that gives each a body deletes the marker byte and the reason. What the paragraph below got right and keeps: the MACHINE is never the reason - kernel/snd.inc:758 osapi_snd_caps answers the constant SND_CAP_TONE | SND_CAP_PCM_EXCL with no kern_small arm ('every machine this OS boots on has a PC speaker'). The draft's greying of Sound On is deleted along with its os88_gfx_pen mechanism, which was wrong in any case: a package never draws a menu item, the kernel's menu_drop greys an item whose string begins with OS88_MENU_DIS (SPEC 12.2, os88api.inc:1945) and dithers it on mono. - sokol_app's OS fullscreen toggle: replaced by os88_fullscreen (SPEC 11.2's WF_FULL latch), the Atari port's F/Esc shape; a refusal (-1: another window holds the latch) toasts

## Budget

- image estimate: 34500
- bss estimate: 5000
- overlay estimate: 0

Basis: CODE by cword's MEASURED density, not its raw line count: cword's shipped code is 35,886 resident + 18,564 overlay = 54,450 minus ~5,400 of .data/.rodata (build/cword.gen.asm's sections) = ~49,000 bytes over 5,205 NON-COMMENT lines = ~9.4 bytes per code line (the draft's 5.6 divided by raw lines including comments). The reference's game section is dense C99 and the ported lines are effectively code lines: time/triggers ~120, vid ~200, move ~120, game ~700, intro ~90, snd ~220, draw ~300, ui/menu/keys ~300 = ~2,050 lines x 9.4 = ~19.3 KB; the C runtime (crt0, trampolines, the thunks used) ~2.5 KB; pmcband.inc ~1 KB -> code ~22.8 KB. DATA (paid on the floppy and in the region): tiles 4,096 + sprites 4,096 (kept whole so sprite numbering is the reference's; the 22 unused sprites are 1,408 B of slack to reclaim first) + palette 128 + mono class 16 + planar table 256 + maze 868 + sound dumps: prelude two voices 245 x 3 B x 2 = 1,470 + death 90 x 3 = 270 + level table 63 + fruit tables ~60 + strings ~500 + about ~300 + menu set 36 + icon 64 + LICENSE incbin ~1,070 = ~13.3 KB. Image ~36 KB by the arithmetic; 34,500 is the estimate after the 1,408 B of unused sprites and the prelude bass's volume column (245 B, carried only if the speaker sampler ever wants it) are the first cuts. BSS: video_ram 1,008 + color_ram 1,008 + packed band scratch 8 x 112 = 896 + planar scratch 4 x 8 x 28 = 896 + mono scratch 224 + dirty spans 72 + sprite state 8 x 8 = 64 + sprite shadow 64 + actors/ghosts ~120 + triggers 22 x 4 = 88 + sound ~60 + input latch/layout/ui ~100 + counters ~16 = ~4,600, rounded to 5,000. The Atari port's 28,160-byte persistent canvas is deliberately NOT carried: the dirty span is exactly the tile set that must be recomposed anyway, so a band scratch composes the same tiles into 896 bytes. Sum ~39,500 of 61,440 - no overlay, ~20 KB spare, and the 50,000 overlay trigger is ~10 KB of growth away (closer than the draft implied); at 50,000 on os88pkg's line pmc_intro.c, game_init/game_round_init and the About text move to ovl_* (CC_HAS_OVL + the third CC_PACKAGE argument, package + .OVL then share a PACCMAN folder on every disk). Worker stack: OS88_STACK_256 with an interrupt floor of 32-38 measured here and 64 on the worst real machine (STACK-SLOTS-PLAN 7.1), so the static chain must stay under ~190: worker frame + pmc_frame + game_tick + game_update_actors + ghost step + can_move at <= 24 bytes each = ~144 plus the blit thunk (~22) and the kernel's gfx_blitp on the caller's stack (~30) = ~196 at the draw, which is called from pmc_frame and not under the game chain, so the two do not stack. The first build's os88pkg line, cc8086's frame table and stkdepth's chain replace every number here.

## Risks

- The whole 'more performant on XTs' case rests on OSAPI_GFX_BLITP AND on three costs the blit does not include: tile/sprite composition (~10 8088 instructions a pixel, so the plan's own 64-tile ceiling could be ~40 ms a frame), the packed-to-planar repack (a lookup and shift/or per packed byte, of the same order as the 5 ms BLITP it feeds) and the C game logic (3.3-6.6 game_tick()s of five actors and ghost AI per frame at C's 3-5x multiplier). A first-principles sum lands near PACMAN.O88's 5.5 fps, not above it. The plan therefore carries NO fps prediction and makes wave 1's MartyPC bench the source of every number; the hypothesis has an explicit pass/fail criterion and both outcomes are publishable facts. If the bench shows the repack dominating, sprites compose straight into planar on the colour path (a 16-px sprite is at most 3 plane-bytes wide per row) and packed stays for the 1bpp adapters only
- BLITP refuses on a 1bpp card, a REAL armed clip region (an overlapping window), a straddle and kern_small, and then the port is on GFX_BLIT4, which at 224 px wide always takes the planar decoder (kernel/vga12.inc:2723): ~41 ms per 8-row band, ~490 ms for a 12-band play frame (~2 fps), ~1.3 s per round-won toggle, ~19 s per round end - an overlapping window costs the game 60% of its frame rate. Both paths are measured and both numbers go in README; the BLIT4 path must stay correct, not merely present; whether the fallback sends sub-64-px chunks on the run path instead is a bench decision, not a guess
- BLITP's 114 us/row-plane and 3.97 us/byte came from Paint's 64x64 and 256x16 shapes; a 224x8 band is 32 row-planes, so the fixed part dominates and the model may be 20% off either way - wave 1's bench brackets the actual band before anything quotes it
- The worker stack is ONE number, OS88_STACK_256, and the tick path must fit it with the interrupt floor (32-38 here, 64 on the worst real machine), the ROM's int 09h chained onto the interrupted stack while a key is held (~40), and the blit thunk plus the kernel's gfx_blitp on the caller's stack (~52) - which is why the chain is flattened by design and MEASURED in wave 2. A 384 request is not the safe alternative: only two 384 slices exist, a request is satisfied by 'the smallest free slice that is at least that big, or refuses' (os88api.inc 2057), and a refused spawn is a game that never starts. If the measured water mark exceeds 208, the class moves to 384 as a recorded, measured decision with that refusal mode stated in SPEC - and that is the one finding the plan could not close on paper
- A real clip region is one of BLITP's refusals and SPEC 5.4.3.3 says only a REAL one refuses; the port draws unclipped only when os88_wm_obscured says nothing covers it, and arms the clip + BLIT4 otherwise. If wm_obscured and the clip disagree for a window partly over the dock strip (the KEEPH overlap), pixels could be drawn over the dock - check the Hercules/CGA overlap rows on the glass and with a click on the dock under the window
- The layout depends on WF_KEEPH hanging 1/3/7 rows over the dock (SPEC 11.93); wm_dock_snap leaves a window that does not fit above the strip, and wm_dock_under repaints the dock under it on every dock repaint - a cost on every toast and dock change to look at, and a shape no C package has used yet
- Two-word time: since() saturates at 0x7FFF for compares and since_lo() wraps for masks; a blink written against the saturating helper freezes after 9 minutes of one round or one attract screen, and the harness's 40,000-tick attract is what catches it
- The one input divergence (a press latched until the next frame's poll) is a new rule of the port's own: a tap becomes exactly one frame of 'held', nothing more, and a hold released before a junction is forgotten as in the reference. It changes the feel against PACMAN.O88's buffered turn and is stated in SPEC and README; the harness drives both a tap and a released hold so the rule cannot drift back into a buffer
- PMC_CATCHUP_MAX = 2 means game time on a slow frame runs at most 2 OS ticks per frame: at ~5 fps the game is at ~55% speed with up to 8-px jumps per frame; at ~2 fps on the BLIT4 fallback it is at ~22%. It is one constant with the arithmetic beside it, the README states the measured speed per adapter - but it is a feel question no emulator answers; the 86Box XT is where to look, and the stopwatch of the 630-tick reveal is the number
- Static scratch is shared by the worker and the UI task: the band scratch and sprite shadow are touched only under the gfx lock (frame and paint both hold it), the key latch bytes are single-byte writes; nothing else may be shared. A static that both contexts write is the RunCPM alias bug (LESSONS.md 13)
- The score/status strips and the fruit list are ROM tiles like everything else, so a stray vid_* write every tick that changes nothing must NOT mark - the compare-then-write rule in pmc_vid.c is what keeps the score band out of every frame; the harness's per-frame call count is the check
- The mono class table is a look decision (walls/dots/Pac-Man white, ghost bodies dither, frightened distinguished) that only a screendump on VIDEO=cga and VIDEO=herc can settle; grey rounds to black there (SPEC 39.4)
- The pill blink coalesces columns 1..26 into one 208-px span in bands 6 and 26: cheap on BLITP (bytes are ~4 us each), ~41 ms per band on the BLIT4 fallback every 8 game ticks - stated, and the reason the per-band span (not a per-tile mask) is kept: on BLITP width is nearly free and the mask would only save composition
- The window frame width (224 + chrome; the Atari port asks 338 for 320) is a wave-1 measurement, not a known number; with os88_wm_snap the content origin is on 8 so no alignment slack is needed
- Name collisions: none - `paccman` does not occur anywhere in the tree; but `make paccman` vs `build/pacman.o88` differ by one letter and a typo silently builds the other program; SPEC section 91 is checked at write time (89 is the last today) and checkdocs.py rejects a citation to a heading that does not exist
- The reference is a transient scratchpad copy: the committed pmc_rom.c (with the 0f5ec5a hash in its header) is the build's truth, the extractor refuses an unpinned checkout, and the --check is run once in wave 1 before the copy disappears; a build with no checkout prints a note and never fails
- Sound is sampled once per OS tick: an effect shorter than ~3 game ticks can vanish entirely between samples (the reference's eat-dot alternation is 5 ticks); the per-voice register trace in the harness shows what was sent, and the reduction is stated rather than tuned. The prelude's melody is voice 1 of the dump and its bass voice 0 - the harness asserts the melody's Hz by name so the voices cannot be swapped again
- The budget is ~39.5 KB by cword's measured ~9.4 bytes per code line, and the 50,000 overlay trigger is ~10 KB of growth away rather than ~20; the first build's os88pkg line replaces the estimate and is tracked in the PR from the first commit
- tests/paccman.py's fixtures depend on wave-2 test-tree work that no existing row has done (dispapps._map with -I build/, `_pmc_*` names) and the stack assertion on t_stkclass following a C shim; both are named files with an owner in wave 2, not assumptions

## What shipped

One paragraph per wave, written when that wave landed and re-measured at the
end of wave 4 against the build that shipped. SPEC.md §91 is the contract and
carries the same numbers; this is the record of how they were arrived at.

**Wave 1 — assets, window, video RAM, the band renderer, its two gates.**
`tools/paccman_assets.py` decodes the reference's five ROM tables and two
register dumps at commit `0f5ec5a` into the COMMITTED `apps/paccman/pmc_rom.c`
(`--check` reproduces it byte for byte and the extractor refuses an unpinned
checkout); the shim, icon, LICENSE and Game menu; `video_ram`/`color_ram` with
per-band dirty spans; `pmcband.inc`'s composer; one blit per band through the
new `os88_gfx_blitp` thunk with its probe on a colour display, `blit1` on
monochrome, `blit4` when either refuses; `os88_wm_display` as the second new
thunk; `WF_KEEPH` frames of 307 rows (163 on CGA). `os88pkg image=21844
bss=4498` — 26,342 of 61,440. The band bench landed here and its first reading
was the wave's finding: `GFX_BLITP` is **6.6×** `GFX_BLIT4` on a 224×8 band and
the packed-to-planar repack costs six times what the blit saves, so the colour
path is a wash and the plane arm was chosen anyway *so that the wave which
removes the repack has something to remove it from*. The plan's own model was
4× wrong in the other direction, which is LESSONS.md 13 exactly.

**Wave 2 — the tick path, the ghosts, the sprite layer, the stack.** The

the worker's deadline loop, the press latch, `pmc_move.c` and `pmc_game.c`

two-span damage model. `image=37332 bss=5188`, 42,520. The chain measured

`t_stkclass` learned to follow a `cc/crt0.asm` shim, which stopped paccman,

**Wave 3 — the attract screen, the sequences, the sound.** `intro_tick` at the

40,000-tick attract is what catches that), the fade as a two-byte cut, three

**Wave 4's review, and what it changed.** Five things, each with a number
behind it. (1) **The row merge reached the tile layer only** — the SPRITE layer
still sampled alternate rows, which is where Pac-Man's circle lost its top and
bottom caps, so `_pmc_sprite` took the same `zmask` argument and the same
formula. The one row that has no partner (source row 15, always the last drawn)
is split off and asked for unmerged, because the routine does not bound its
read. It costs a sprite row **+20%** and the arm that does not merge **one test
a source byte** (+3.9% of a sprite row, 0.9% of a VGA play frame), and it took
the CGA play-frame cost of the whole merge from +3.9% to **+7.5%** against the
25% bound. (2) **A whole `W_PAINT` with the About card up composed all 36
bands** and then covered 20 of them (VGA) or 34 (CGA) with the card: 1,008
tiles, ~1.1 s of VGA XT drawn and immediately hidden. `pmc_repaint` marks the
card's COMPLEMENT now — `pmc_ab_box` answers the rectangle for both callers,
with the slack the opposite way round for each — and the harness gained the
card-up row it never had, which is why the defect lived. (3) **SPEC's
chunked-lock arithmetic left the game logic out**: `os88_worker` brackets the
whole of `pmc_frame`, so the first chunk is up to six `game_tick`s plus four
bands, a measured **387.4 ms** and not the ~279 four bands would be. It is a
harness row with a 460 ms bound now rather than a sentence. (4) **The merge's
cost to the picture was recorded for letters and not for digits** — merged `S`
is 1 pixel from `5` and 1 from `6`, merged `5` is 2 from `6`, and the attract
screen's `50 PTS` legend photographs as `60 PTS`. Neither arm satisfies "the
text reads": the merge is better on letters and worse on digits and is kept on
that balance, stated. (5) Two instruments: `tests/paccman.py`'s call-counting
pass was a third of a call low on both ports (it discarded an unclassified
stop), and its four API-slot offsets are parsed out of `apps/os88api.inc`
instead of copied. The re-take is the table above; the worker's stack water
mark moved **178 → 188** with it, which is 18 bytes under the 208 bar.

**"Maybe this port is more performant on XTs" — no**, on none of the three,
and the row prints that sentence either way rather than gating on it. The
reasons are all measured rather than argued: the repack ahead of the fast blit
costs 41.78 ms a band against the blit's 7.36; one `game_tick` is 18.6 ms and
a frame carries three; and this port draws the arcade's 28×36 field where §89
draws Roklan's 40×22, so the fps column is not a like-for-like race. The one
column PaccMan holds is effective game SPEED, and only on VGA (24% against
23%), which is `PMC_CATCHUP_MAX` = 2 doing what it was put in for; on both 1bpp
adapters §89 is at its deadline and asleep.
