# `.cold` in ROM: fixups, sizes, the call graph and how often the image moves

**A measurement, not a description.**
- **When and where:** taken 2026-10-04 on a four-core cloud container
  (Xeon, 2.1 GHz). The tree was `351461a` on branch `rom-plan` (`elendilon`'s
  head, build 358), built with a plain `make`.
- **Who uses it:** docs/plans/ROM-PLAN.md was written from it.
- **What kind of figures:** every number is a property of the ASSEMBLED
  BYTES. No emulator was run and no time was measured.
- **Scope:** it is true of that tree and is not maintained against later ones.
  `tools/os88romfix.py` re-takes sections 1-3 on any built tree in about nine
  seconds.

## 2. Fixups: every place the running kernel names `.cold`'s segment

**Method.** `tools/os88romfix.py` copies `kernel/` aside and splits
`COLD_SEG` into two values:
- `COLD_RAM`, which places the ladder rung;
- `COLD_CS`, which is the segment the code executes in.

It assembles each kernel at `COLD_CS` = F601 and F702, which are 0x101 apart,
and diffs the two binaries.

A site is counted only if it passes both checks:
- the two lengths must be identical;
- every differing byte must belong to a little-endian word that moved by
  exactly 0x101.

**No byte failed either check on either kernel.**

| section | `kern_big` | `kern_small` |
|---|---:|---:|
| `.text` | 94 | 60 |
| `.ovl` | 24 | 7 |
| `.ovlw` | 7 | 3 |
| `.boot2` | 1 | 1 |
| `.cold` | 10 | 2 |
| `.modc` | 21 | — |
| `.modu` | 19 | 12 |
| `.modl` | 49 | 43 |
| `.modh` | 26 | — |
| `.modf` | 6 | 6 |
| `.modp` | — | 63 |
| `.modd` | — | 15 |
| **total** | **257** | **212** |

The sites inside `.cold` follow, with the opcode three bytes before the word.
`0x9A` is `call far ptr16:16`.

**`kern_big`:**
- `mod_disarm.slot+0x7`: the store `mov word [di+2], COLD_SEG`.
- `dsk_xfer.notch+0x5`: a `SPLCALL` expansion, `cmp word [spl_fseg], COLD_SEG`.
- Far calls (`0x9A`):
  - `ld_pkg_byname.have+0xd`
  - `fcp_xfer.more+0x8`
  - `fcp_xfer.fin+0x5`
  - `fdlg_seed.media+0x17`
  - `fdlg_reap_x.here+0x2b`
  - `desk_select.chg+0x22`
  - `sc_open.run+0x5`
  - `hb_ok_x+0x6`

**`kern_small`:** only the first two, `mod_disarm.slot+0x7` and
`dsk_xfer.notch+0x5`.

## 3. `.cold` carries no build number

The kernel was assembled at build 358 and again at build 999. Both have
three-character strings, so the comparison isolates the VALUE. The bytes that
differ:

| section | `kern_big` | `kern_small` |
|---|---:|---:|
| `.text` | 5 | 5 |
| each module header | 2 | 2 |
| `HIBER.DRV` (`.modh`) | 4 | — |
| `.cold` | **0** | **0** |

A commit by itself does not re-cut a ROM image. What re-cuts one is any
change that moves a `.text` or `.bss` symbol that `.cold` names, which is
section 5.

## 4. Call graph across a `.cold` split, `kern_big`

**Method:**
- `ndisasm` over the `.cold` bytes.
- Every near `call`, `jmp`, `jcc` and `loop` target is resolved to a symbol
  through a nasm `[map all]`.
- Each symbol is assigned to the `kernel/*.inc` that defines its global name.
  1,706 bytes of macro-generated labels have no owner file and are counted
  with the ROM half.
- Because of that attribution, the per-file totals differ slightly from
  `kernsize --modules`. `kernsize` is the authority for sizes.

**The candidate cut:**
- **ROM half, 32,465 bytes:** the file system cluster and what it calls
  densely. That is `files`, `disk`, `diskw`, `memory`, `fdlg`, `assoc`,
  `desk`, `driver`, `filecp`, `mod`, `drvvol`, plus the unattributed labels.
- **RAM half, 5,533 bytes:** `apps`, `vga12`, `loader`, `lz`, `hiber`,
  `desksc`, `blank`, `ctrl`, `menu`, `wm`, `instance`, `dock`, `extmod`,
  `clone`, `ui`.

**163 jump and call sites cross the cut.**
- **55 go into symbols `kernel.asm` defines in `.cold`.** These are mostly the
  `cw_*` shims out to `.text`, and they could exist once per half.
- **The largest crossings that remain:**

  | from | to | sites |
  |---|---|---:|
  | `files.inc` | `clone.inc` | 12 |
  | `loader.inc` | `memory.inc` | 6 |
  | `desk.inc` | `desksc.inc` | 7 |
  | `loader.inc` | `disk.inc` | 5 |
  | `loader.inc` | `assoc.inc` | 5 |
  | `ctrl.inc` | `mod.inc` | 5 |
  | `driver.inc` | `wm.inc` | 6 |

- **The densest edges inside the ROM half**, which is why they stay together:

  | from | to | sites |

  | `files.inc` | `kernel.asm` shims | 79 calls and 54 jumps |

  | `files.inc` | `disk.inc` | 16 |

  | `filecp.inc` | `disk.inc` | 15 |

## 5. How often `.cold` changes: 192 commits of `elendilon`'s first-parent line

**Method:**
- Each commit was checked out in a scratch worktree.
- Its `kernel.asm` was assembled for both kernels, against TODAY'S `build/`
  generated includes. A tree that predates an include, or that has no
  `KERN_SMALL` arm, fails or assembles identically for both, and was
  excluded.
- The `.cold` bytes were hashed.
- 131 of the 192 commits are usable, from 2026-08-12 to 2026-10-04.

**The caveat:** an older tree built against a newer generated include can
differ from what it shipped with. That can add a spurious change, or hide a
real one. The count is therefore an ESTIMATE of the rate, not a ledger.

| since | kernel | commits | `.cold` changed | distinct images | commits per image |
|---|---|---:|---:|---:|---:|
| 2026-09-01 | `kern_big` | 82 | 32 | 33 | 2.5 |
| 2026-09-01 | `kern_small` | 82 | 23 | 23 | 3.4 |
| 2026-09-20 | `kern_big` | 45 | 17 | 18 | 2.5 |
| 2026-09-20 | `kern_small` | 45 | 11 | 12 | 3.8 |
| 2026-09-29 | `kern_big` | 36 | 15 | 16 | 2.2 |
| 2026-09-29 | `kern_small` | 36 | 9 | 10 | 3.6 |

section 1.3):

Of the 21 days with an integration commit since 09-01, `kern_big` was over
40,780 on 8. `kern_small` never was.

**A second sample on a different stretch** told the same story. That was 30
consecutive kernel-touching commits of one day (2026-09-30, a kernel size
pass, every commit included and not only merges):
- `kern_big`'s `.cold` changed on most of them;
- `kern_small`'s stayed identical for 12 in a row.
