# VESABENCH on a 486: is the BIOS window switch the cost?

**A measurement, not a description.** Taken 2026-10-22 on 86Box 6.0's
`vm/486-vesa` - an AMI 471 board, i486DX2/66, 8 MB, a Cirrus Logic
CL-GD5428 on the VL bus whose BIOS (`CL-GD542X VGA BIOS 1.41`) is VBE 1.2 -
booting `make vesabench`'s disks: `vesabench.img` (`VESA.DRV` wanted, Auto)
with `vxbench.img` in B:, whose `\AUTOSTRT` link opens `VESABNCH.O88`. The
driver chose **1024x768 at 16 bits a pixel** on that card. The package ran
its rows on its first paint and saved `VESABNCH.TXT` beside itself; the
file was read back off the image with `mcopy`. Built at the plan's S7
(branch `feature/vesa`, PR #295). It is true of that tree and that machine
and is not maintained against later ones. 86Box prices a VL-bus write
through its own model, so the absolute figures are the emulator's; the
ratios between rows are what this settles.

## What it settles

**The BIOS call is not the cost. The pixels are.** `int 10h AX=4F05h` is
**7.00 us** a call; a 624x200 fill at 16bpp is **23.3 ms** and crosses seven
64 KB windows, so the switches are 49 us of it - **0.2%**. The plan's S7
said the direct `dispi` window register for the Bochs VBE would be taken if
and only if the count said the BIOS call was where the time went. It did
not, and the register is **not taken**: on this card there is no such
register anyway, and on QEMU's the saving would be a few microseconds a
frame against the ~130 bytes of probe and port code it would cost.

**Where the time does go is the bus.** The fill already runs one `rep
stosw` to the window edge, and 249,600 bytes in 23.3 ms is **10.7 MB/s**
into video memory - 12 cycles a word on a 66 MHz 486, which is a VL-bus
write cycle and nothing the driver can shorten. Every row below is a
multiple of that rate.

## The rows

| `FILL 624x200` | 4 | **23,342** | 117 us a row, 0.187 us a pixel - 10.7 MB/s |

QEMU's run of the same disk (`tests/vesabench.py`, host speed, not a time)
reads the same shape: the BIOS call under a microsecond, BLIT4 at 5x BLITD
(1,010 against 193 us).

## What the measurement changed

The depth blit and the restore copied a word at a time with a window-edge
test after each (`movsw; VXW; loop`), at 5.1 MB/s against the fill's 10.7.
They copy with one `rep` to the window edge now, then the next window, then
the rest (`vx_rowcopy`): BLITD 7,856 → 6,787 us with `rep movsb`, and
**3,436 us** with the words under `rep movsw` and only the odd byte under
`movsb` - 2.3x, and the fill's rate to within 10%. The restore is every
menu's and every dialog's close, so this is the row that reaches a user.

## What it does not say

Nothing here is an 8088 figure and none will be: a packed display is a 386
or better by construction (§120.1). No real VBE card has been booted; the
Cirrus is 86Box's model of one, and a real card's `4F05h` on a real bus is
the first thing a field run would add. The 15bpp packing is unmeasured
because neither QEMU nor this card offers a 15bpp mode.
