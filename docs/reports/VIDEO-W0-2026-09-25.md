# Video Player, wave 0: what a frame, a stream and a frame interrupt cost

**A measurement, not a description.** Taken 2026-09-25 on a four-core cloud
container, on the tree at `3ac8ec79` plus the vidsnd bench that landed beside
this report. MartyPC was at its pinned commit (`e15cb04f`). Every figure is
GUEST time, counted by the emulator's cycle-exact 4.77 MHz 8088, so it holds
at any host load. It is true of that tree and is not maintained against later
ones. It answers docs/plans/VIDEO-PLAN.md section 8's wave 0, and the plan's
sections 2.2 to 2.4 were rewritten from it.

The content is the owner's five XDC streams (BADAPPLE, THUNDERC, TRONDISC,
BBBB_BW, BBBBCOMP), used by permission. They are not in the tree. XDC is
MobyGamer's (MIT, © 2014 Jim Leonard).

The instruments are three benches and their drivers, all `soak` rows:
- `tests/vidbench.py` for (a) and (d);
- `tests/viddisk.py` for (b);
- `tests/vidsnd.py` for (c) and (e);
- `tools/os88vid.py`, which reads the streams.

## The three questions and their answers

1. **Can operands beat code?** On disk, yes: 21–46% less. On CPU, close:
   - the worst frames cost 1.01–1.28× XDC's own code;
   - frames of long spans are faster than XDC's code;
   - the mean frame costs 2–7 points more of the machine.
2. **Can today's file API stream it?** No, and the reason is measured.
   `OSAPI_FILE_READ_AT` slows by **142 ms per MB of offset**, so a 57.7 KB/s
   stream fails ~2 MB into the file. A read that keeps its place is the fix
   (VIDEO-PLAN 4.2).
3. **Does a Sound Blaster 2.0 give one interrupt per frame?** Yes: 30.01/s
   and 60.02/s at XDC's two shapes. Hardware ADPCM is unanswerable here,
   because MartyPC's Sound Blaster has none.

## (a) The frame decoder, against XDC's own code

`tests/vidbench/vdec.inc` decodes the format of VIDEO-PLAN 2.2. The rows:
- XDC's frame program, far-called exactly as `XDC_PLAY.PAS` calls it;
- our decoder writing the screen;
- decode to a RAM shadow, then copy the dirty band to the screen;
- both decoders into RAM.

**The picture is checked first.** Every frame is applied to a black canvas by
both decoders and compared with the host's checksum. Every timed frame
matched on both paths. Broken on purpose (a 3-byte store one byte short), the
check failed every frame holding a 3-byte change, and only those.
`os88vid verify` separately reproduces all **11,192 frames** of the five
streams exactly, in sequence.

**One construct at a time.** The synthetic frames repeat one kind of change
60–400 times. Cycles each, MartyPC CGA 5150, writing CGA memory:

| construct | XDC | ours | |
|---|---|---|---|
| a frame, fixed | 309 | 1,214 | ten list heads |
| 1-byte change | 36.0 | 49.6 | +13.6, the skip byte |
| 2-byte | 50.8 | 65.2 | +14.4 |
| 3-byte | 72.0 | 89.1 | +17.1 |
| 4-byte | 88.0 | 104.8 | +16.8 |
| 6-byte | 126.0 | 146.1 | +20.1 |
| 16-byte slice | 378 | 372 | |
| 40-byte slice | 895 | 804 | `rep movsw` against `rep movsb` |
| 16-byte run | 277 | 309 | |
| 40-byte run | 638 | 621 | |
| an isolated change in its own skip segment | — | ~+215 | the reason for absolute segments |

**Raw stores**, 8,000 bytes, cycles a byte:

| | to CGA memory | to RAM |
|---|---|---|
| `rep movsb` | 21.6 | 18.0 |
| `rep movsw` | 18.0 | 13.1 |

CGA's wait states cap any long fill at ~18 cycles a byte.

**Real frames**, cycles, CGA memory. These are the heaviest frames by XDC's
own model, and the heaviest by ours:

| frame | XDC | ours | ratio |
|---|---|---|---|
| BADAPPLE 443 (XDC's heaviest) | 89,317 | 59,943 | 0.67 |
| THUNDERC 640 | 108,408 | 100,338 | 0.93 |
| TRONDISC 333 | 112,140 | 105,034 | 0.94 |
| BADAPPLE 3513 (our heaviest) | 81,723 | 104,862 | 1.28 |
| TRONDISC 396 | 102,363 | 123,870 | 1.21 |
| THUNDERC 48 | 98,737 | 114,561 | 1.16 |

The same rows on MartyPC's XT VGA come out lower, because that emulated VGA
has no wait states: XDC's heaviest frame runs at 0.48× there.

**Whole streams.** The measured per-construct costs above were applied to
every frame:

| stream | disk, XDC → ours | file | CPU mean, XDC → ours |
|---|---|---|---|
| BADAPPLE | 93.8 → **57.7 KB/s** | 20.1 → **12.3 MB** | 14.8% → 21.5% |
| THUNDERC | 92.8 → 72.9 | 6.9 → 5.4 | 24.4% → 26.8% |
| TRONDISC | 105.1 → 80.8 | 5.0 → 3.8 | 27.0% → 30.3% |
| BBBB_BW | 42.1 → 22.9 | 0.3 → 0.2 | 5.9% → 9.4% |
| BBBBCOMP | 46.4 → 28.0 | 0.3 → 0.2 | 7.9% → 11.3% |

**What the measurements changed.** VIDEO-PLAN 2.2 records every change:
- **Four lists became ten.** The four-list design measured +40–60 cycles for
  a short span, all of it `rep` start-up.
- **Absolute segments.** Half of all segments held one entry, at ~215 cycles
  of set-up each.
- **No row splits.** The splits had turned the heaviest frames into ~290 runs
  where XDC has one `rep stosb`.
- **Hidden runs** are extracted.
- **Unrolled span loops.** They took a 16-byte run from +66 cycles to +32.

**A decoder was built and REFUSED.** The row-table translator that placed a
canvas on another layout at playback cost **~480 cycles per row change**, 3–12×
XDC on real frames. Layout moved to the host.

**Shadow-and-copy costs 3–5× a native decode at full screen,** because the
dirty band spans nearly the whole screen on this content. It suits a small
Live window, or a foreign file at a reduced display rate.

## (b) Streaming off the fixed disk

This was measured on `os8088_5150_herc_hdd_sb_gla`, booted off a VHD holding
a 12.6 MB `STREAM.DAT`. **Its controller is XT-IDE, which moves every byte
with the CPU. The owner's ST-225 on an ST11M is a DMA controller.** The chain
walk is CPU on both machines; the transfer rate is this controller's.

| row | ms a call | KB/s |
|---|---|---|
| `READ_AT` 32 KB at 0 MB | 219.7 | 145.7 |
| at 3 MB | 622.5 | 51.4 |
| at 6 MB | 1,071.1 | 29.9 |
| at 9 MB | 1,501.3 | 21.3 |
| at 12 MB | 1,922.4 | 16.6 |
| `int 13h`, one 26-sector track | 54.9 | 236.7 |
| `int 13h`, one sector | 4.6 | 109.2 |

The walk grows **141.9 ms per MB of offset**. That is SPEC.md 18.4.4's
stateless re-walk, priced.

## (c) One interrupt per frame

The drivers are suspended and the DSP and DMA channel 1 programmed by hand:
auto-init over a double buffer, DSP block = one frame's audio. The card was
found at 220h, IRQ 7 (discovered with DSP F2h), DSP 2.01.

| shape | interrupts in 5.00 s | per second |
|---|---|---|
| PCM8 22,050 Hz, 735-byte block (30 fps) | 150 | 30.01 |
| PCM8 8,040 Hz, 134-byte block (60 fps) | 300 | 60.02 |
| ADPCM4 22,050 Hz, 368-byte block (DSP 7Dh) | 0 | — |

The ADPCM row is zero because MartyPC's Sound Blaster (`sblaster.rs`) says so
in its own header: *"no ADPCM"*. **Whether a real SB 2.0 plays 4-bit ADPCM
auto-init at 22 kHz is a field question.** The bench carries the row so that
a field run answers it.

## (e) How much of each frame the disk leaves

The card plays PCM8 at 30 fps. Its interrupt handler burns a fixed share of
each frame with interrupts off, standing in for the decode, while the
foreground reads whole tracks through the ROM's `int 13h` for 5 s:

| interrupt burns | tracks | KB/s | of the unburnt rate |
|---|---|---|---|
| 0% | 90 | 234.1 | 100% |
| 25% | 65 | 169.1 | 72% |
| 50% | 42 | 109.2 | 47% |
| 75% | 17 | 44.2 | 19% |

On a CPU-copied disk the reader gets roughly what the interrupt leaves.
BADAPPLE's mean decode (~22% of a frame, above) leaves this controller
~175 KB/s against the 57.7 it needs. **The owner's DMA controller is the case
this cannot measure**; there the transfer proceeds under the interrupt, and
the curve should be nearly flat.

## Emulator facts that bound every figure above

- **MartyPC charges Hercules memory exactly what it charges CGA's**, to the
  cycle. Every Hercules row above equals its CGA twin. The field measured
  Hercules at 40–49 cycles a word (SPEC.md 88.3.6), so on iron a Hercules
  frame is somewhat slower than these rows say.
- **MartyPC's XT VGA has no wait states.** A VGA "screen" row equals its RAM
  row.
- **MartyPC's fixed disk is XT-IDE.** No DMA hard-disk controller is modelled
  (tools/martypc/configs/os8088_machines.toml, `os8088_5150_herc_hdd_sb_gla`).
- **MartyPC's Sound Blaster has no ADPCM.**

The owner's 5150 answers what this cannot:
