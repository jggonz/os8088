PRODUCT AND TECHNICAL CONTRACT

WaveRack records from a supported sound input, plays sound, displays an editable waveform, and saves WAV files. It is a compact, hardware-inspired companion to XTMP3 in the os8088 desktop. Its styling combines native striped title bars and bitmap typography with a silver faceplate, recessed black instruments, tactile transport keys, white/green segmented digits, cyan/white selection handles, and restrained pixel bevels.

Target original 8088/8086-class real-mode hardware, including a 4.77 MHz XT, using existing repository conventions. No x87/8087 dependency and no 80186+ opcodes in the baseline package. Host tools may use modern libraries or floating point; target audio, rendering, and editing paths must work with integer arithmetic. If optional newer-CPU optimizations are justified later, keep them isolated and guarded so the original XT still works.

Inspect AGENTS.md, build scripts, package format, examples, UI/event APIs, file dialogs, filesystem, allocation and segment rules, timer/scheduler behavior, and sound drivers. Use the actual native APIs; do not assume DOS services, a C runtime, an available ADC, full duplex, stereo, DMA, or Sound Blaster support. A digital recording input requires capture-capable hardware and a working driver. Detect this capability and provide honest read-only/playback behavior when it is absent.

Start with uncompressed PCM WAV: 8-bit unsigned and 16-bit signed little-endian; mono and stereo files. Default recording to 11,025 Hz, 8-bit mono only when the device supports it. Offer actual supported input rates and formats rather than arbitrary options. Full quality on a capable device is welcome; on slow machines use explicit, correctly timed playback conversion when necessary. Do not change pitch by playing a file at a different clock without resampling. Compressed WAV codecs and MP3 encoding are outside the initial scope; reject unsupported codecs clearly rather than interpreting them as PCM.

Use a streaming document design so useful recordings are not limited to free RAM. Keep bounded audio buffers, waveform caches, and edit metadata; use disk-backed temporary storage and undo as appropriate. Establish a measured code/data/stack budget after inspecting the OS. Do not assume the separate XTMP3 project's 400 KB budget is available here. Preserve desktop responsiveness, minimize redraws, and never perform filesystem I/O or UI rendering in an audio interrupt.

PHASE 1 — NATIVE PACKAGE, VISUAL SYSTEM, AND THREE LAYOUTS

US-01 — As an os8088 user, I can install and launch WaveRack like any other native application.

Acceptance:

- Open a native WaveRack window, handle focus, redraw/expose, move/resize where supported, and close cleanly.
- File/Edit/View/Sound menus exist and meaningful state is visible. Unsupported/incomplete commands are disabled rather than fake-working.
- Closing returns audio devices, handles, temporary files, memory, and system state safely; unsaved work is handled once document support exists.
- Build integration does not break unrelated packages.

Verification: native launch/close smoke check, package install, resource cleanup, baseline opcode/disassembly audit where tooling permits.

US-02 — As a user, I recognize the same WaveRack application in color and monochrome.

Acceptance:

- Controls respond to mouse and keyboard and use real state; no full-window bitmap masquerading as an interactive UI.

PHASE 2 — DOCUMENTS, WAVEFORMS, AND PLAYBACK

US-04 — As a user, I can open a WAV file and inspect the sound without loading the entire recording into RAM.

Acceptance:
- Native New/Open dialogs, file identity, dirty indicator, duration, rate, bit depth, channels, and current position are accurate. A filename dropdown may hold recent documents if consistent with the OS.
- Parse RIFF/WAVE chunks robustly, including extra/unknown chunks, arbitrary valid chunk order, odd-byte padding, and bounded lengths. Validate PCM format, block alignment, data size, and overflow in sample/byte arithmetic. Reject truncated, malformed, unsupported, or excessive-size inputs safely.
- Use integer sample-frame indices as the canonical timeline unit. A frame contains one sample per channel; selection/edit/export offsets must respect block alignment.
- Display real amplitude data and an overview. Use cached min/max envelopes so transients are visible when many samples map to one pixel. At close zoom, display sample detail rather than a fabricated waveform.
- A mono file has one genuine waveform; stereo display or a clearly labeled combined envelope must not silently discard one channel. Do not fake a second channel.
- Zoom in/out, fit-to-window, overview navigation, and horizontal scrolling preserve appropriate time focus and readable ticks. Generate/update envelope data in bounded work units.
- Long file loading remains cancelable and responsive, with measured bounded memory.

Verification: generated mono/stereo fixtures, odd-sized chunks, unknown metadata, malformed bounds, large-file streaming, known impulse/tone envelopes, exact sample-frame/timeline mapping.

US-05 — As a user, I can play, pause, stop, seek, and adjust listening volume at the correct pitch and speed.

Acceptance:
- Play starts from the cursor or selected range according to clear documented rules. Pause retains position; resume continues; Stop stops output and restores a documented cursor position.
- The readout, waveform cursor, overview, and actual audio output remain synchronized. Seeking resets/flushes output buffers safely.
- Use supported audio-output formats and buffer scheduling. Convert format/rate explicitly where necessary and show actual output capabilities; never silently reinterpret source bytes or change pitch.
- The VOLUME slider affects playback/monitor loudness, not stored samples. Prefer a driver mixer where available; use a measured bounded software path otherwise.
- Handle EOF, pause/resume, device unavailable/busy, read failure, and underrun without stale samples or loud DC steps. Count/report underruns in diagnostics.
- Keep audio servicing isolated from painting and file-dialog work. No file reads, large copies, or waveform processing in interrupt handlers.

Verification: generated audio with known duration/frequency, sample-count checks, playback state transitions, seek edges, silence conventions, volume independence from document data, and actual output on an available device. A mock backend verifies logic only and must be labeled as such.

PHASE 3 — CAPTURE, LEVEL, AND INPUT GAIN

US-06 — As a user with capture-capable hardware, I can record from a supported microphone or line input and retain the recording.

Acceptance:
- Query/report capture capability. List only supported sources, rates, channels, and depths. If capture is missing, disable Record with an explanation while preserving file playback/editing.
- Add a minimal reusable OS capture abstraction/driver extension if needed and feasible from available hardware documentation; do not hide direct hardware access inside UI code or simulate recording as a finished feature.
- Before recording, choose/confirm the destination or an appropriate disk-backed scratch policy and check free space. Do not assume the boot drive or that a whole recording fits RAM.
- Default to a new take; if recording into an existing document is offered, explicitly define append/insert/overwrite behavior. Protect existing unsaved work through Save/Discard/Cancel.
- Record, Pause, resume, and Stop have correct state transitions. Finalize frame counts/header lengths on Stop. Disk-full, write failure, overrun, cancellation, and device loss preserve an explicitly marked recoverable result where safe.
- A recording updates the timer and waveform incrementally at a sustainable redraw rate. Capture continuity takes priority over decorative animation.
- Do not require full duplex. Disable monitor-through-playback when the device cannot support it. Do not automatically enable live speaker monitoring that could cause feedback.

Verification: capture-backed recording and WAV replay on available hardware; deterministic injected capture data for buffer/error tests; honest report of missing physical-device testing.

US-07 — As a user, I can see the active signal level and set input gain independently of listening volume.

Acceptance:
- One horizontal segmented LED-style meter sits directly above the INPUT GAIN slider, matching all layouts. Use green/yellow/red in color and filled/outlined/patterned cells in monochrome.
- Compute a lightweight documented peak level from actual active samples; use integer thresholds or a small lookup instead of runtime logarithms or floating point. Use consistent reference/units, normally a dBFS-style scale to 0, and a short peak-hold/clip indication.
- Meter updates are throttled and not dependent on drawing once per sample. Its source is clear: capture when armed/recording, playback when playing, inactive when neither is running.
- INPUT GAIN uses a hardware capture gain control when exposed by the driver. If software gain is supported, identify it clearly and apply it to the capture data path with saturation; it cannot undo or prevent ADC clipping. Disable unsupported gain controls instead of displaying a placebo.
- Gain, volume, and source selections are separate settings. Changing gain does not retroactively alter existing audio; changing playback volume does not change the recording level or saved data.

Verification: fixed amplitude and clipping fixtures, meter thresholds/peak reset, genuine gain-capability behavior, gain-volume independence, and mono/color visibility.

PHASE 4 — SELECTION AND USEFUL EDITING

US-08 — As a user, I can select a precise range, audition it, and loop it.

Acceptance:
- Click to place the cursor; drag to select; adjust handles; show start/end and length consistently in main waveform and overview. Allow keyboard adjustment and exact-value entry via a compact dialog if needed.
- Define ranges as [start, end) sample-frame indices, clamp to document boundaries, and handle zero-length/full-file selections without off-by-one errors.
- Loop selection repeats the selected sample range correctly, not the entire file. Define cursor/loop behavior when no range exists. Pause/Stop/seek remain reliable during looping.
- Selection boundaries remain stable across zoom/layout changes. Text values and playhead reflect real sample times, not a fixed drawing from the mockup.

Verification: ranges at start/end, single-frame and empty ranges, stereo alignment, zoom/resolution changes, and repeated loop sample counts.

US-09 — As a user, I can remove unwanted audio, keep a selected excerpt, and undo mistakes.

Acceptance:
- Implement Trim (keep selection), Delete (remove selection and close the gap), Cut/Copy/Paste, Select All, and at least one reliable Undo/Redo step. A bounded multi-step disk-backed history is preferable if resource costs are reasonable.
- Trim/Delete are direct buttons as shown; other editing commands can live in Edit. Disable commands when their preconditions are absent.
- Preserve channel alignment, format, document duration, selection/cursor rules, and envelope-cache correctness after edits. Clipboard paste with incompatible audio must either perform a documented conversion or refuse with a clear reason; never reinterpret bytes.
- Use bounded edit metadata/piece references or streaming rewrites rather than demanding a full memory copy of long files. Keep immutable source regions alive while undo still references them.
- Stop or safely coordinate audio before an edit. Do not silently mutate the active playback buffer or write over uncommitted source content.
- Optional silence insertion and fades may follow the required editing commands; do not let extra effects delay a complete recorder/editor.

Verification: exact sample fixtures for edit/undo/redo, stereo boundary checks, long-file edits under constrained RAM, failures/cancellation, and envelope/selection invalidation.

PHASE 5 — SAVING, FORMATS, AND RECOVERY

US-10 — As a user, I can save the recording or edited selection as a valid WAV file without losing my source.

Acceptance:
- Save, Save As, and optional export-selection use native dialogs and accurate format/disk-size information. Prompt before replacing another existing file and never silently overwrite the source during an intermediate edit.
- Write temporary output, stream edited regions, finalize RIFF/data lengths and padding, flush/close, and replace/rename safely using actual filesystem capabilities. If replacement cannot be atomic, document and handle the safest supported sequence.
- Format controls have clear semantics: recording configuration for a new take, source metadata for an opened file, and explicit conversion/export choices. Changing “11k/8-bit/Mono” must not silently reinterpret existing sample data.
- Offer only implemented conversion combinations. Include saturation and appropriate filtering for downsampling; show whether a conversion changes the saved document or only playback.
- Check destination, writability, free space, filename rules, and file-size limits using overflow-safe arithmetic. Cancellation or failure leaves the original intact and incomplete output clearly identified.
- Closing a dirty document uses Save/Discard/Cancel. Delete only scratch files owned by this job; preserve unrelated data. On restart, identify recoverable unfinished recordings if the implemented filesystem/process model permits it.

Verification: reopen saved files with an independent host WAV reader, exact frame counts/format, export-selection, odd data length, replacement failure, disk-full mid-write, canceled save, source preservation, and dirty-close behavior.

IMPLEMENTATION GUIDANCE

Use repository-appropriate modules with clear boundaries: native UI/layout/theme; bitmap-font/resource loader; document/edit/undo model; bounded RIFF/WAV parser/writer; waveform envelope/rendering; audio transport/capture/output; device capabilities; streaming/scratch management; and diagnostics/test harness. These are responsibilities, not a demand for an unnecessarily large abstraction hierarchy or predetermined filenames.

Maintain a central transport state machine (Idle, Playing, Playback paused, Recording, Recording paused, Busy, Error) and document/dirty state separately. Define which commands are enabled in each state. Do not permit contradictory Record/Play states on a half-duplex device. Selection, view range, playback position, recording write position, gain, and volume are different values and should not overwrite one another.

Keep data paths format-aware: 8-bit PCM silence is 128; signed 16-bit PCM silence is zero; stereo uses complete sample frames. Use wide/checked arithmetic for file sizes, sample counts, and timestamps, implemented using valid 8088 operations where needed. Avoid expensive conversion or division per painted pixel/audio sample when cached integer calculations suffice.

A host-buildable model and mock device are valuable for fast deterministic tests, but they do not replace the native package or real driver integration. If physical capture hardware is unavailable, implement what can be established from actual APIs and documentation, mark that acceptance verification pending in the PR, and never label a generated waveform as a microphone recording.

For every story: implement the smallest complete user outcome, verify the meaningful acceptance criteria, commit, update the plan and draft PR, then continue. Preserve the supplied visual language while making layout choices that genuinely fit hardware limits. Do not stop at scaffolding, a plan, or beautiful nonfunctional screenshots.
